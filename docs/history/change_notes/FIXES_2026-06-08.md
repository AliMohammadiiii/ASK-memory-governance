# Fixes 2026-06-08 — T4/Ollama accuracy + latency

Diagnosed from the incomplete `m4w13_50_t4_ollama` run (11/50 graded, ~285 s/question,
`Supersede=0` across 349 actions). Root causes and fixes below.

## What was wrong in that run
- **`controller_prior_top_k=1`** → every candidate was compared against the single
  *newest same-type* memory (semantically unrelated), so the relation classifier
  returned `independent` 280/297 times and **Supersede never fired** — the whole
  knowledge-update mechanism was inert (e.g. Fitbit "9 months" lost to stale "6 months").
- **`controller_include_assistant_context=False`** → the single-session-assistant
  competency (~32% of the slice) was structurally unanswerable; those questions
  could only return `Unknown`.
- **Retrieval `k=5`, no neighbor window, no answer retry** → low recall, many
  spurious `Unknown` answers on answerable questions.
- The validated accuracy knobs already existed as the **`max-a10g`** quality preset
  in `run_baseline.py`, but that preset is HF-only and the Ollama/T4 path rejected it.
- Turning the knobs on increases per-question LLM calls, and the run already could
  not finish 50 on a T4 — so a latency lever was needed too.

## Changes
1. **`src/ksa/pipeline/orchestrator.py`** — new `prior_similarity_threshold` field.
   In the semantic-prior path, a prior is only sent to the (2-stage) relation
   classifier when its cosine similarity to the candidate is `>= threshold`.
   Below it the pair is treated as independent **without an LLM call**. This both
   cuts the dominant per-question cost and stops the small classifier from
   hallucinating `support`/`contradict` on unrelated pairs. `0.0` = old behaviour.
2. **`scripts/run_baseline.py`** — new `--controller-prior-similarity-threshold`
   flag, wired into the orchestrator, the scorecard manifest payload, and the
   `max-a10g` preset (set to `0.45`).
3. **`scripts/run_m4w13_ollama.py`** — exposed the missing knobs on the Ollama/T4
   path (`--k`, `--controller-retrieval-neighbor-window`,
   `--controller-prior-similarity-threshold`) and added a `--quality t4` profile
   that enables the validated accuracy knobs at T4-affordable levels:
   assistant context on, answer-retry on, `prior-top-k=3` with a `0.45` similarity
   gate, retrieval `k=10`, `+/-1` neighbor window; extraction still bounded at 32.
   Explicit flags override the profile. All new fields are recorded in the manifest.
4. **`tests/test_pipeline_orchestrator.py`** — added
   `test_prior_similarity_threshold_gates_unrelated_relation_calls`: Supersede still
   fires on a genuinely-related prior while the unrelated prior is skipped without
   an LLM call.

Full suite: 336 passed, 2 skipped. `ruff` clean.

## Run command (T4 quality)
```bash
python scripts/run_m4w13_ollama.py \
  --model-profile t4 --quality t4 \
  --systems controller \
  --slice data/slices/longmemeval_s_cleaned_50_seed0.jsonl \
  --out runs/m4w13_50_t4_quality \
  --embedder-backend sentence_transformer \
  --resume
```
`--resume` reuses the cached extraction/relation/answers, so re-running after a
Colab disconnect continues where it left off. For a faster wall-clock, run the
five systems split across session shards with `--session-workers N` **and** start
Ollama with `OLLAMA_NUM_PARALLEL=N` (watch T4 VRAM with the 9B answerer).

## Throughput (deploy/run_colab_m4w13_t4_ollama.sh)
The first run sat at ~285 s/question with the GPU near 0% util — the cause was
Ollama running with `OLLAMA_MAX_LOADED_MODELS=1`, so the interleaved
extraction(llama)→relation(phi)→answer(qwen) calls forced a model unload/reload
on nearly every step. The new T4/Ollama Colab runner keeps all three role models
resident (`MAX_LOADED_MODELS=3`), serves concurrent requests
(`NUM_PARALLEL=3`), runs `SESSION_WORKERS=3` disjoint session shards then merges
(grades identical to serial), and embeds MiniLM on the GPU (`EMBEDDER_DEVICE=cuda`).
Defaults target a 24 GB A10/L4; lower to 2/2 on a 16 GB T4. The run is resumable
and zips its outputs at the end. See `deploy/COLAB_M4W13_T4_RUNBOOK.md`.

## Answer-layer fix — recency tie-break (from grading the first 11 answers)
The graded run showed the dominant error was the answerer returning `Unknown` on
answerable questions (5/8 non-abstention) plus one stale knowledge-update value
("6 months" instead of "9 months"). The retrieval/over-abstention misses are
covered by the `QUALITY=t4` knobs (assistant context, k=10, neighbor window,
answer-retry, prior-top-k+supersede). The remaining answer-layer gap was that the
retrieved-memory block carried no timestamp, so when two values of the same slot
both survived retrieval the answerer could not pick the newest. Fixed:
- `src/ksa/baselines/prompts/recency_pruning.j2` now renders each retrieved item's
  timestamp (guarded with `is defined` so the recency baseline, which omits it,
  still renders).
- `src/ksa/pipeline/orchestrator.py` passes `timestamp` into the retrieved block
  and `DEFAULT_SYSTEM_PROMPT` now says: "When the same fact appears with more than
  one value, prefer the value from the memory with the most recent timestamp."
- Tests: `test_controller_answer_prompt_includes_retrieved_timestamp` plus a
  `most recent timestamp` assertion in the prompt-content test.

This complements Supersede: even if the classifier fails to fire Supersede, both
values reach the answer prompt with timestamps and the newer one wins.

## CRITICAL fix — answerer context-window truncation (from the first T4 run)
The first `QUALITY=t4` run scored **8% (1/13)**: every prediction was a single
token (`"9"`, `"I"`, `"$"`, ...). Diagnosis from the predictions: `completion_tokens=1`
and `prompt_tokens=2047` on every row. The answerer `OllamaLLM` was built without a
`num_ctx`, so it used the **2048 default**. The quality prompts (assistant context +
k=10 + neighbor window) reach ~8k tokens, which filled the whole 2048 window — Ollama
truncated the prompt and left **one token** to generate. (Extraction/relation were
fine; they use `--structured-num-ctx 4096` on tiny prompts. Supersede even fired:
`505af2f5` had `Supersede: 2`.)

Fixes:
- `scripts/run_baseline.py`: the answerer now takes `--ollama-num-ctx` (default 8192)
  and passes it to `OllamaLLM`.
- `scripts/run_m4w13_ollama.py`: `--ollama-num-ctx` passthrough; the `t4` quality
  profile raises it to **16384** (≈2× the largest observed prompt). Recorded in the
  manifest.
- `src/ksa/inference/ollama.py`: `_warn_if_context_exhausted` prints a loud warning
  whenever the prompt fills `num_ctx` and ≤1 token is generated, so this silent
  failure can never tank a whole run unnoticed again.
- Tests: `test_ollama_warns_when_prompt_fills_context` +
  `test_ollama_no_truncation_warning_on_healthy_generation`.

Note to watch in the re-run: `answer_retry_on_unknown=True` is in the quality bundle.
For abstention questions (gold = "information not enough") the correct answer is
"Unknown"; the retry prompt pushes the model to answer when retrieved evidence exists,
which *could* corrupt the abstention competency (3/3 in the original run). If
abstention accuracy drops in the re-run, disable it with `--no-answer-retry-on-unknown`.

## P4 (first slice) — deterministic temporal scaffolding
After the 50-q run (50%, temporal-reasoning the weakest at 3/12), added a pure,
fully-unit-tested temporal module (`src/ksa/controller/temporal.py`) and wired it
as **additive, gated scaffolding** (NOT a hard bypass — the answerer stays
authoritative, so it cannot turn a right answer wrong):
- `--controller-temporal-scaffold` (on in `--quality t4`): for temporal questions
  it appends a "NORMALIZED EVENT DATES" block built from dates parsed out of the
  memory TEXT (the event date, e.g. "Coastal Cleanup on March 7") rather than the
  session timestamp (when it was discussed), plus a reference 'today' proxy (the
  most recent session date) for "X ago"/"last week" phrasing.
- Validation (no GPU needed): replayed on the real failed question `f0853d11`, the
  module surfaces 2023-02-21 and 2023-03-07 as in-text event dates (gold = 14 days
  between; the model had guessed 21). Unit tests pin the math for the actual failed
  run dates (14/1/7 days, Apr 1/10/15 ordering): `tests/test_temporal.py`.
- Caveat: it only helps when the event dates are present in the retrieved text; a
  hard deterministic answer + true `question_date` (the dataset field, dropped by
  the current slice) is the next step and needs a slice rebuild from source +
  on-GPU validation. The roadmap is in
  `NOTES/m4w13_50_t4_quality_analysis_and_roadmap.md`.
