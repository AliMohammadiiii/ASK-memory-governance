# Controller / eval correctness fixes (2026-05-30)

Forensic root-cause pass over the m4w13 LongMemEval smoke run. The headline
symptom ("controller mostly wrong, Supersede=0") was **not** an extraction or
relation bug — extraction is healthy (0/226 empty) and `Supersede=0` is the
documented `_find_prior` limitation (the prior is the newest same-type item from
another session, so the relation classifier correctly returns "independent").
The real causes were a memory-coverage gap, a silent memory-drop bug, a judge
gap, and mild over-extraction. All four are fixed below.

**Guardrail:** every fix is verified MGP-6-safe. MGP-6 uses its own decision
path (`scripts/run_mgp6.py`), direct-label scoring (not the LongMemEval judge),
and clean-assertion extractions — so none of the validated MGP-6 numbers change.

## Fixes

1. **Judge: abstention + "Unknown" handling** — `src/ksa/eval/longmemeval.py`
   - LongMemEval abstention golds all open with *"The information provided is
     not enough."*; the controller answers *"Unknown"* for no-info questions.
     Neither was recognised, so correct abstentions were graded wrong.
   - Added `"unknown"`/`"not enough"` refusal markers and the
     `"is not enough"` family to abstention-gold detection.
   - Effect (re-grading the 7 completed smoke rows): **1/7 -> 3/7** correct; the
     two `_abs` rows flip wrong->correct, no false flips. MGP-6 unaffected.

2. **Controller: stop silent memory drop** — `src/ksa/pipeline/orchestrator.py`
   - On KEEP, the old rule dropped any candidate the classifier rated
     non-"independent" against the (often unrelated) newest-same-type prior —
     silently discarding **44/226** genuine memories on the smoke run.
   - Now KEEP only suppresses a **near-verbatim duplicate** of the prior;
     distinct facts are always committed. MGP-6 uses its own execute path.

3. **Extraction: drop question/request paraphrases** — `src/ksa/extraction/extractor.py`
   - Small models emit ~12% question/request items ("Which one is best?",
     "Can you plan a class...") that are not durable assertions and pollute
     memory. Added a **start-anchored** filter so a declarative turn carrying a
     real fact (even if it ends with "?") is preserved.
   - Verified against the validated MGP-6 rerun: **0/177** recorded MGP-6
     extracted items are affected.

4. **Coverage: opt-in assistant-turn context** — `src/ksa/pipeline/orchestrator.py`
   - ~32% of LongMemEval answers live in **assistant** turns the user-only
     pipeline can never capture (the whole single-session-assistant competency).
   - New flag `--controller-include-assistant-context` (default **off**) adds
     raw assistant turns from the allowed corpus to the retrieval pool. Raises
     the slice's answerable ceiling from ~28/50 to ~36/50. Default off => MGP-6
     and validated runs unchanged.

## Round 2 — detailed answer analysis (after the 40% run)

Inspecting every wrong answer + its retrieved context on the 10-row run:

5. **Judge: verbose golds reached only the token guard, never the LLM judge** —
   `src/ksa/eval/longmemeval.py`. `352ab8bd` answered **"20%"** (correct) but the
   gold is a 13-token sentence, so the token guard ("prediction must contain
   every gold token") hard-rejected it before the LLM judge. Fix: the hard
   reject now fires only for **short golds** (<=4 content tokens); verbose golds
   fall through to the LLM judge. Flips `352ab8bd` -> correct (projected
   **4/10 -> 5/10 = 50%**); short-gold mismatches and the hallucinated
   abstention (`2133c1b5_abs`) correctly stay wrong. MGP-6 unaffected.

6. **Retrieval: assistant turns were embedded whole** —
   `src/ksa/pipeline/orchestrator.py`. The 1-3k-char assistant turns added by
   the coverage fix were one vector each, matching broadly but burying the fact
   and crowding short user-fact turns. Now sentence/line-**chunked** (<=320
   chars) so the fact-bearing snippet ranks and the answer prompt stays focused.

7. **faiss is now optional** — `src/ksa/baselines/flat_vector_store.py`. Falls
   back to an exact numpy inner-product index when `faiss-cpu` is absent
   (verified bit-identical top-k), so a fresh Colab kernel no longer crashes in
   retrieval. `sentence-transformers` is still required (it is the embedder).

Remaining wrong answers are genuine answerer/retrieval limits of the 8B model
(multi-session arithmetic "$50 more than goal", counting "2 fun runs",
9-vs-6-months, failure-to-abstain), not pipeline bugs — they need a stronger
answerer or the published LLM judge, both out of surgical scope.

## Parallel execution on A100 (speedup)

Session-level parallelism: `--session-workers N` runs N independent
`run_baseline` processes over disjoint **round-robin** session shards (each its
own sqlite/caches/action-log), then merges into one report. Per-session grades
are identical to a serial run (each grade depends only on its session's content
+ deterministic, temp-0 model calls; the cross-session cache is pure
memoization) — only wall-clock changes. New: `scripts/run_baseline.py`
`--num-shards/--shard-index`, `src/ksa/eval/merge.py`, and the launcher flag.

The Ollama **server** must allow concurrent requests, so start it with
`OLLAMA_NUM_PARALLEL` before running:

```bash
pkill ollama 2>/dev/null; sleep 2
OLLAMA_NUM_PARALLEL=8 OLLAMA_MAX_LOADED_MODELS=2 \
  nohup ollama serve > /content/ollama.log 2>&1 &
sleep 8

cd ksa_gpu_run_package/ksa_controller
python scripts/run_m4w13_ollama.py --model-profile thesis \
  --slice data/slices/longmemeval_s_cleaned_50_seed0.jsonl \
  --out runs/m4w13_full --systems all \
  --seed 0 --n-bootstrap 1000 \
  --embedder-backend sentence_transformer --embedder-model all-minilm:l6-v2 \
  --controller-include-assistant-context \
  --session-workers 8 \
  --ollama-host http://127.0.0.1:11434 --ollama-timeout-s 900 --judge-timeout-s 900
```

Pick `--session-workers` ≈ `OLLAMA_NUM_PARALLEL` (8 is a good A100 default for
8B + a 3.8B judge). Output (`runs/m4w13_full/<system>/`) is the merged report,
identical in content to a serial run.

### If Ollama times out under parallelism

`--session-workers 8` issues 8 concurrent 8B generations to one GPU; a single
A100 cannot hold 8 KV-cache contexts, so `/api/chat` requests stall and hit the
900 s timeout. Fixes: keep `--session-workers` and `OLLAMA_NUM_PARALLEL` at
**3–4** on one A100, or use the HF backend below.

### HuggingFace backend (no Ollama)

`scripts/run_m4w13_hf.py` runs the model in-process (no Ollama server, no HTTP
concurrency limits) and now supports the same `--session-workers` and
`--controller-include-assistant-context` flags:

```bash
cd ksa_gpu_run_package/ksa_controller
python scripts/run_m4w13_hf.py --systems all \
  --slice data/slices/longmemeval_s_cleaned_50_seed0.jsonl \
  --out runs/m4w13_full_hf --seed 0 --n-bootstrap 1000 \
  --hf-model meta-llama/Meta-Llama-3-8B-Instruct --hf-dtype float16 \
  --embedder-backend sentence_transformer \
  --controller-include-assistant-context \
  --no-controller-raw-turn-fallback \
  --judge-backend ollama --judge-model phi3.5:3.8b \
  --session-workers 2
```

Caveat: each shard process loads its **own** copy of the model into GPU memory,
so for an 8B fp16 model on one A100 (80 GB) the ceiling is ~2-3 shards (add
`--hf-load-in-4bit` to fit more). For real throughput at higher concurrency,
serve once with **vLLM** (continuous batching) — out of current scope.
`run_m4w13_hf.py` defaults to a same-as-answerer judge and raw-turn fallback;
pass `--judge-backend ollama --judge-model phi3.5:3.8b` and
`--no-controller-raw-turn-fallback` for a clean (non-confounded) run.
