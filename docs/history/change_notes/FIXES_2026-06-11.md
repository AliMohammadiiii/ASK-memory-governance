## 3 (analysis). Prompt-budget diagnosis — **context saturation is real but rare**

**[verified] Exactly ONE session truly saturated the window:** `852ce960`
(knowledge-update) — `prompt_tokens=32767 = num_ctx−1`, `completion_tokens=1`,
`raw_prompt = 208,527 chars` (≈ 50–63k true tokens, clamped by Ollama). It
answered `"$"`. Retry did **not** fire because `"$"` ≠ `"Unknown"`. This is the
single case the `prompt_tokens=32767 fills num_ctx=32768` warning fired on.

**[verified, corrects the working hypothesis] `eac54add` and `gpt4_45189cb4` did
NOT saturate.** Each retry attempt was ~21–26k tokens (under 32,768); they
retried on `"Unknown"` and still returned `"Unknown"`. Their failure is
retrieval/selection/noise, **not** running out of context room — which is why
raising ctx to 32k did not help and why **prompt-slim (less noise), not a bigger
window, is the right lever**.

**[verified] The other 4 wrong cases** (4f54b7c9, 5d3d2817, e493bb7c,
gpt4_59c863d7) had 11–19k-token prompts — comfortably within the window. These
are reasoning/aggregation/selection errors (count 3 vs 5; previous vs current
role; "above my bed" vs "in my bedroom"; "3" vs "five model kits"), not budget
problems.

**[verified] No prompt-budget guard existed.** No `budget/trim/ctx/reserve`
fields anywhere in `extras`; `OllamaLLM._warn_if_context_exhausted` only *warns
after the fact*. Prompts were allowed to exceed `num_ctx` (52,866 and 42,436 ≫
32,768).

| File | Change | Why (which §9 trigger) |
|---|---|---|
| `src/ask/pipeline/orchestrator.py` | Added a **pre-send prompt-budget guard** (`_answer_token_budget`, `_budget_trim_for_answer`, `_estimate_prompt_tokens`) + per-sample budget logging in `extras` and progress log; extended the answer retry to also fire on an **empty** answer; both initial and retry prompts now use the budget-trimmed context. | Missing/broken prompt-budget guard; retry behavior masked truncated output; logs insufficient to diagnose saturation. |

| `deploy/run_colab_m4w13_a10g_ollama.sh` (new) | Profile-aware A10G Ollama wrapper: maps `PROFILE=a10g`/`QUALITY=a10g` → the validated t4 model set + accuracy bundle, sets 24 GB throughput defaults, forwards all flags. | A10G Ollama runner was missing (existing a10g scripts are HF-only; the Ollama wrapper rejected `PROFILE=a10g`). |
| `tests/test_prompt_budget.py`, `tests/test_quality_preset_flag_override.py` (new); `tests/test_failed_slice_builder.py` (extended) | Pin the three behaviors above. | Cover new code. |

The prompt-budget guard is a **no-op when the backend exposes no `num_ctx`**
(the FakeLLM in tests) and when the prompt already fits, so existing behavior is
byte-stable. It only triggers for over-budget prompts (i.e. `852ce960`). `B4`
(`NaiveOverwriteBaseline`) subclasses `ControllerOrchestrator`, so it inherits the
guard; `B1/B2/B3` are unaffected (B1 has no retrieval; B2/B3 retain the post-hoc
Ollama warning).

### Budget guard behavior
- Reserves `max(256, min(max_new_tokens, 512))` output tokens (= 512 here) plus a
  256-token margin; trims retrieved context until the **estimated** prompt fits
  `num_ctx − reserved − margin`.
- Trims noisiest-first, **never** the question/turns: assistant-role context →
  lowest-score items (where neighbor-expanded / raw-context items land) → keeps a
  floor of the 3 highest-scoring hits.
- Token estimate is **approximate** (`chars / 3.3`, a deliberate upper bound) and
  every log line / extras flag says so.

Per-sample logging now emitted (in `extras` of `predictions.jsonl` and in the
progress log): question, `prompt_num_ctx`, `prompt_reserved_output_tokens`,
`prompt_generation_budget_tokens`, `prompt_estimated_tokens(_before_trim)`,
`prompt_memory_items_before/after_trim`, `prompt_trimmed`,
`prompt_assistant_context_included`, `prompt_neighbor_window`,
`answer_text_length`, `answer_looks_truncated`, `answer_retry_used`,
`prompt_token_estimate_is_approximate`, plus the inline `raw_prompt`.
