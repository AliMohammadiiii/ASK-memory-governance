## 1. What was built, why, and how

### 1.1 The question the instrument has to answer

Every mainstream memory benchmark scores a *downstream answer*. That is the
wrong measurement for a write policy: a wrong answer can originate in retrieval,
context assembly, generation, or the write decision, and an aggregate answer
score cannot say which. Isolating the write decision requires holding retrieval,
context, and generation constant and varying only the evidential situation:

> Given the same stored record and the same proposed new value, can a system
> distinguish the case where the proposal is stale (KEEP), the case where it is
> current (SUPERSEDE), and the case where the evidence cannot settle the
> question (ABSTAIN)?

That requirement — not scale, coverage, or realism — dictated the construction.
MGP-6 v4.3 is small and synthetic *on purpose*; the control it buys is the only
reason it can answer the question.

### 1.2 Why v2 had to be replaced

In v2, each conflict family mapped deterministically to one action. Family-
disjoint splits blocked *literal* overlap while leaving the family-to-label rule
intact in every split. Consequence: a conflict-type-only lookup fitted on
train+dev reaches **1.0000** held-out accuracy while never reading the dialogue
or memory state (type-only 0.9667). Scenario recognition was sufficient;
evidence reasoning was never tested.

Two lessons carried into the redesign. Mechanical repairs (schemas, identifiers,
hashes, manifests) were kept strictly separate from the substantive content
redesign, so a passing structural check could not be mistaken for a repaired
construct. And review moved to the level of the *group of items sharing a
scenario*: a leak is a property of the contrast between the KEEP, SUPERSEDE, and
ABSTAIN variants, not of any one item.

### 1.3 The item

Five fields, schema `additionalProperties: false`:

| Field | Content |
|---|---|
| `public_id` | opaque identifier, `MGP43-` + 20 hex characters |
| `memory_before` | stored record: `principal`, `memory_slot`, `standing_value` |
| `dialogue` | 9, 11, or 13 turns alternating USER/ASSISTANT, each with a `turn_id` |
| `evaluation_query` | fixed instruction naming the slot and the three permitted actions |
| `gold_action` | KEEP, SUPERSEDE, or ABSTAIN |

The closed schema is a design commitment, not housekeeping: no conflict-type
field, no design target, no component label, no annotator note — no channel of
the kind that leaked the answer in v2. The identifier is opaque so it encodes
nothing recoverable.

Dialogue shape is fixed: early turns state the standing value and name the
candidate value; a middle turn declares which positions in a numbered evidence
list are **indexed** to the target slot and warns the rest belong to neighbouring
records; the list is read out; a closing turn restates the requested value.

### 1.4 The semantic component — the load-bearing idea

A **semantic component** is nine items sharing one `principal`, one
`memory_slot`, one `standing_value`, and one candidate value, arranged as a
3 x 3 grid: three dialogue lengths (9, 11, 13 turns) x three gold actions.
Verified directly on the released public splits:

- **40/40** public components are exactly 3 KEEP / 3 SUPERSEDE / 3 ABSTAIN
- each dialogue length is exactly **40 KEEP / 40 SUPERSEDE / 40 ABSTAIN**

So neither verbosity nor length carries any signal — a shortcut that trips many
synthetic benchmarks, closed by construction rather than by audit.

What varies inside a component is narrower still. All nine items draw evidence
from a **byte-identical pool of six sentences** (verified **120/120**
(component, length) triples). The three actions differ *only* in **which two of
the six sentences the dialogue indexes to the target slot**. Across the 80
triples where the index statement parses mechanically, the three indexed pairs
are always distinct and always **partition the pool exactly** (80/80).

### 1.5 A worked component

`principal = Rohan`, `memory_slot = status message`,
`standing_value = available`, candidate `do not disturb`. All nine items contain
the same six sentences and the same closing turn. Only the index differs:

| Indexed pair (the two sentences bound to the slot) | Gold |
|---|---|
| "The do-not-disturb period has an expiry record." + "After the expiry, Rohan writes that his status is available." | **KEEP** |
| "Rohan writes that the temporary period has ended." + "He then changes the status entry to do not disturb." | **SUPERSEDE** |
| "The retained records do not include the offsets needed to compare them." + "The expiry time and the status-change time use different time zones." | **ABSTAIN** |

Each pair demands a different kind of reasoning:

- **KEEP** — a temporary override expired and the standing value was reasserted
  *after* it; the proposal is stale.
- **SUPERSEDE** — the temporary period ended and a durable change followed; the
  proposal is current.
- **ABSTAIN** — the timestamps are in different time zones and the retained
  records lack the offsets to compare them. The evidence is not *weak*, it is
  **unresolvable**. This is why the 300 ABSTAIN items carry a dual ambiguity
  flag: designed unresolvability, not annotator uncertainty.

The other four sentences remain in every item as **controlled distractors**. A
system reading the transcript rather than the index finds apparent support for
all three actions in all three items. The confound is not removed by
paraphrase — it is removed by holding surface form fixed and moving only the
pointer. That is what makes v4.3 a *controlled* synthetic benchmark rather than
merely a synthetic one.

### 1.6 Splits and determinism

Components, never items, are assigned: train 180 items / 20 components, dev
180 / 20, hidden 540 / 60. Each of 20 domains contributes one component to
train, one to dev, three to hidden. Split seed 4301. The build is
byte-deterministic — archive timestamps pinned to 1980-01-01, so identical
inputs yield identical hashes. No system can see the KEEP variant of a scenario
in training and the SUPERSEDE variant at test.

### 1.7 The release gates are executable, not narrative

**Shortcut audit** — fitted on train, evaluated on hidden, component-held-out,
five seeds (4301-4305). Word- and character-level TF-IDF logistic regressions
over **twelve restricted views**, plus punctuation-only and length-only numeric
features, plus decision trees at depths 1-5. Pre-set ceilings:

| View | Ceiling | View | Ceiling |
|---|---:|---|---:|
| `full_text` | 0.65 | `assistant_only` | 0.45 |
| `dialogue_only` | 0.65 | `first_three` | 0.50 |
| `target_evidence_only` | 0.65 | `query_only` | 0.40 |
| `last_two` | 0.50 | `memory_only` | 0.40 |
| `candidate_only` | 0.45 | `id_only` | 0.40 |
| `previous_turn` | 0.45 | `punctuation_only` | 0.40 |
| `user_only` | 0.45 | `length_only` | 0.40 |
| `depth3_tree` | 0.60 | | |

Result: `failed_gates = []`. Two views matter especially. `id_only` confirms the
opaque identifiers leak nothing — the exact failure class that made v2's
conflict-type field fatal. `target_evidence_only` is the strictest
self-criticism in the build: even the *correctly indexed* evidence, stripped of
dialogue context, must not linearly separate the classes.

**Duplicate audit** — SHA-256 over seven restricted views, failing on *any*
cross-split collision in the five decision-relevant ones; plus character TF-IDF
(4-6 grams) cosine over every cross-split pair, failing at >= 0.995. Components
share an evidence pool by construction, so within-split near-duplication is
expected and permitted; the gate targets cross-boundary leakage specifically.

**Public/private boundary** — public records exclude gold labels, design
targets, component metadata, private identifiers, and annotator metadata. Hidden
inputs, hidden gold, human gold, annotation packets, private mappings, and
restricted-view audits live only in a gitignored local boundary. Merkle roots:
final gold `437b2a26...`, annotations `a7e59f88...`.

### 1.8 Human validation and the weight it can bear

Two independent packets cover all 900 items. The builder does not accept them on
trust. Each row must carry a schema version; a `content_hash` matching the
coordinator binding; a permitted action; a **non-empty list of evidence turn
identifiers that all reference real turns in that dialogue**; a rationale of at
least 20 characters; confidence in [0,1]; boolean ambiguity and exclusion flags;
an annotator identifier; a timezone-aware timestamp. Coverage must be exactly
900, no duplicates. Any violation aborts the build with `RuntimeError`.

The evidence-turn requirement is the substantive one — it makes an annotation
*checkable against the item* rather than a bare label.

Outcome: agreement on every action (raw 1.0, Cohen's kappa 1.0), 0 exclusions,
0 adjudications, mean confidence 0.96 / 0.967, all 300 ABSTAIN items flagged as
intentionally ambiguous.

**What this establishes and what it does not.** Perfect agreement on a task whose
labelling rule is deterministic by construction certifies the manual is
followable and the items instantiate it. It does **not** independently validate
the construct: two annotators applying the same unambiguous rule agree whether or
not the rule measures memory governance. Completion is owner-attested; the
builder validates records, coverage, hashes, and agreement, not reviewer
identity or duration.

### 1.9 Why the design makes errors interpretable

Because the three actions within a component are surface-matched, an error names
its own mechanism. Predicting SUPERSEDE on the KEEP variant means the system read
a sentence present in the item but indexed to a different slot.

Tested directly: of the 28 errors the frozen controller makes on the development
split, 18 resolve mechanically against a sibling item's indexed pair (same
component, same length, gold action equal to the *predicted* action). In **all
18**, the evidence supporting the predicted action was present but not indexed.
**Every resolvable error is distractor capture** — precisely the failure the
component design isolates. The instrument measures what it was built to measure,
a stronger statement than any accuracy figure below.

This also explains the hidden-split confusion profile in section 3: ABSTAIN is
the hardest action (0.7889 recall) because its indexed pair asserts
*unresolvability* while four distractors continue to assert resolvable KEEP and
SUPERSEDE readings.

### 1.10 What the construction cannot deliver

The control is bought by giving up realism. Constructed scenarios do not
reproduce natural user interactions — the dialogues are stylized evidence-list
recitations, not conversation. The design is single-slot and single-step, so it
cannot test interference between records or multi-turn write trajectories. It is
English-only. Human completion is owner-attested rather than
identity-authenticated. And there is **no selected public redistribution
license**, so it must not be publicly hosted until licensing is resolved. v4.3
is a controlled diagnostic to be paired with an external benchmark such as
LongMemEval (section 8), never a substitute for one.

## 3. Error decomposition — the main analytical finding

For a write-governance system the **asymmetry** of the errors, not their total,
is the operational result.

| Governance error | Count / denom | Rate | Wilson 95% CI |
|---|---:|---:|---|
| Action false commit (gold ABSTAIN acted on) | 38/180 | 0.2111 | [0.1578, 0.2764] |
| — ABSTAIN to KEEP (**state preserved**) | 30/180 | 0.1667 | [0.1193, 0.2280] |
| — ABSTAIN to SUPERSEDE (**state corrupted**) | **8/180** | **0.0444** | **[0.0227, 0.0852]** |
| Missed update (gold SUPERSEDE not applied) | 15/180 | 0.0833 | [0.0511, 0.1329] |
| Destructive overwrite (gold KEEP superseded) | 11/180 | 0.0611 | [0.0345, 0.1061] |
| Unnecessary abstention (gold KEEP/SUPERSEDE abstained) | 24/360 | 0.0667 | [0.0452, 0.0973] |

An ABSTAIN-to-KEEP error leaves the stored state byte-identical to what
abstention would have produced — only the audit record of declining is lost. An
ABSTAIN-to-SUPERSEDE error actually replaces an active record on insufficient
evidence. Collapsing both into one "false commit" rate of 0.2111 **overstates
the state-corrupting harm roughly fivefold**.

**Disclosed defect.** Selective accuracy (0.8449) is *below* overall accuracy
(0.8481). A well-calibrated selective predictor shows the opposite ordering.
The abstention mechanism performs governance (avoiding unjustified writes)
without performing selective-risk targeting; these are different capabilities
and must not be conflated.

The gain over naive overwrite is **not uniform**: +8 items on knowledge update,
+5 on single-session preference, +2 on multi-session, +3 on temporal reasoning.
Concentration in exactly the competencies requiring stale-value replacement and
durable-versus-transient preference separation is the strongest available
evidence that the improvement comes from the write decision rather than generic
pipeline differences. A better retriever would not preferentially help
knowledge-update items.

### Pipeline anatomy: where the compute actually goes


The released pipeline traces (`extraction_trace.jsonl`, `relation_trace.jsonl`,
`answers.jsonl`) permit a stage-level decomposition rather than a single
per-item cost figure, and the decomposition overturns the natural reading of the
accuracy table.

| Stage | Model calls | Prompt tok. | Completion tok. | Share of prompt | Model latency |
|---|---:|---:|---:|---:|---:|
| Extraction | 11,847 | 41,806,968 | 1,806,685 | **73.6%** | 19.98 h |
| Relation classification | 19,157 | 10,936,290 | 1,226,921 | **19.2%** | 18.93 h |
| Answer generation | 180 | 4,072,477 | 41,418 | **7.2%** | see note |
| **Total** | **31,184** | **56,815,735** | **3,075,024** | — | 38.91 h |
| Per item | 173.2 | 315,643 | 17,083 | — | 778 s |

Answering the 180 questions takes 180 model calls and 4.07 M prompt tokens.
Reaching the point where those questions *can* be answered takes 31,004 further
calls and 52.7 M prompt tokens. The write-time stages are **92.8% of prompt
tokens and 99.4% of model calls**; the answer stage — the only stage an
end-to-end memory benchmark scores — is 7.2% of the budget.

This reframes the cost comparison above. The governed controller is not an
expensive answerer; it is a cheap answerer sitting on an expensive ingestion
pipeline, and the same holds for naive overwrite. Reporting only answer-stage
tokens, as the retrieval-only baselines invite, measures the 7% and ignores the
93%.

**A correction to how per-item latency must be read.** The `latency_ms` field on
each answer record is **cumulative end-to-end** time for that item, not
answer-generation time. Summing it gives 40.46 h, while summed extraction and
relation model latency is 38.91 h; the 1.55 h difference is the implied
generation-only cost — about **31 s per item**, not the 809 s the field
suggests. Per-item pipeline times quoted in this section use the cumulative
field and must be read as end-to-end pipeline time. This thesis flags the point
explicitly because the naive reading — that one answer call takes thirteen
minutes — is wrong by more than an order of magnitude.

**Extraction is mostly rejection.** Of 11,491 processed turns, **5,656 (49.2%)**
return `no_extractable_content`. The extractor's most common output is
*nothing*, which is correct behaviour on conversational filler and the first
line of defence against memory bloat. The remaining turns yield 11,771 candidate
memories (1.02 per turn overall), typed as 9,144 episodic facts, 2,261 transient
preferences, and 366 stable preferences. Mean extraction confidence is 0.934
(minimum 0.75); 17.4% of candidates carry a hedge marker and 1.3% a negation
marker. Parsing was robust: 370 of 11,491 turns hit a first-parse error, 9
required the repair path, and there were **zero model fallbacks and zero retries
beyond the first attempt**.

**Relation routing is deliberately conservative — and auditable.** The stage is
two-part: stage one labels the candidate against a retrieved prior as
`support`, `contradict`, or `independent`; stage two, invoked on 9,530 of 9,539
classifications, resolves same-subject and temporal ordering. Routing is then
deterministic and every decision records its reason:

| Stage-1 label | Routed relation | n |
|---|---|---:|
| independent | unclear | 8,281 |
| support | support | 880 |
| **contradict** | **supersede** | **221** |
| contradict | contradict | 147 |
| contradict | unclear | 1 |
| parse fallback | unclear | 9 |

All 8,281 `independent` labels route to `unclear` — an independent candidate is
never permitted to displace a prior. Of 369 `contradict` labels, only the 221
that stage two confirms as **same-subject and newer** route to `supersede`; 113
older and 33 same-time contradictions are held as `contradict` without a write.
So **221 of 9,539 classifications (2.3%)** may propose a replacement. This is
the mechanism behind the 397 supersessions (3.1%) in the action log and,
ultimately, behind the controller's low destructive-overwrite rate — the
conservatism is architectural, not emergent.

**Caching did not help, and the trace explains why.** The extraction cache holds
11,477 unique keys against 11,491 traced turns, the relation cache 9,523 against
9,539 classifications — under 0.3% deduplication in both. Each turn is keyed by
its own content and each candidate by its pairing with a specific prior, so in a
single pass over distinct sessions there is essentially nothing to reuse. The
caches are resume insurance, not a throughput optimisation, and any deployment
estimate assuming cache amortisation across a first pass is unsupported by this
evidence.

### Complete system comparison: accuracy, error type, time, and cost

One homogeneous 180-item slice, same corpus, same reader model, same frozen
judge. Accuracy is over all 180 items with the pre-registered bootstrap percentile CIs
(identical to the downstream-validation table, so one canonical interval per
statistic); the error columns decompose those 180.

| System | Acc. | 95% CI | Correct | Wrong answer | Over-refusal | Answered unanswerable | Answer tok. | Ingestion tok. | Latency |
|---|---:|---|---:|---:|---:|---:|---:|---:|---:|
| B1 no-memory | 0.0500 | [0.022, 0.083] | 9 | 1 | 170 | 0 | 0.02 M | — | 1.6 s |
| B2 flat-vector | 0.4444 | [0.372, 0.517] | 80 | 30 | 70 | 0 | 0.65 M | — | 2.5 s |
| B3 recency | 0.2389 | [0.183, 0.300] | 43 | 22 | 115 | 0 | 0.14 M | **43.0 M** | 3.1 s |
| B4 naive-overwrite | 0.6333 | [0.561, 0.700] | 114 | 49 | 15 | 2 | 2.56 M | n.d.‡ | 966.0 s |
| **ASK controller** | **0.7611** | [0.700, 0.822] | **137** | **25** | 17 | 1 | 4.07 M | **52.7 M** | 809.2 s |

‡ B4's relation stage ran (9,339 classifications recorded) but its trace carries
no per-call token or latency telemetry, and its relation cache shares **zero**
keys with the controller's, so the cost was incurred independently and cannot be
recovered. It is reported as not determined rather than as zero or as an
estimate. B1 and B2 have no LLM ingestion stage: B2 retrieves over embeddings.

Three findings here are invisible from an accuracy ranking.

**1. Accuracy conflates two very different failures.** Decomposing the 180 items
separates a *wrong answer* from a *declined* one. B1 with no memory is not merely
inaccurate — it refuses 170 of 171 answerable items, which is correct behaviour
for a system with nothing to retrieve, and its 5% comes almost entirely from
correctly declining the 9 unanswerable items. B3 refuses 115. Read as accuracy
these look like the same failure as a wrong answer; they are not. The controller
and naive overwrite are the only two systems that commit to answers at scale, and
between them the decisive number is the wrong-answer count: **25 against 49**.
The controller roughly halves wrong answers (−49%) while adding two
over-refusals; a paired exact McNemar test restricted to wrong answers gives
b = 31, c = 7, **p = 1.2 × 10⁻⁴**.

**2. Committing more often did not break calibration.** On the 9 by-design
unanswerable items, naive overwrite answers 2 and the controller answers 1. The
counts are too small to separate; they are reported because a system that commits
more often should be checked for exactly this failure, not because 2 versus 1 is
a result.

**3. The expensive part is ingestion, not governance.** This most changes the
cost story. B3 recency — a baseline whose whole premise is cheapness — runs an
extraction stage of **43.0 M prompt tokens, 3% MORE than the governed
controller's 41.8 M**, and scores 23.9% against 76.1%. Extraction is the dominant
cost and is common to every write-time system. The governance machinery proper
(relation classification) is 10.9 M tokens — a **26% marginal increment** on
extraction — and that increment is what separates 23.9% from 76.1%. The
controller does have the largest total prompt cost (56.8 M against B3's 43.2 M)
because it is the only system running both stages; the point is not that
governance is free but that it is a small fraction of a cost every
memory-maintaining system already pays. Framing governed writes as *the*
expensive option misplaces the accounting: what is expensive is deciding what a
turn contains.

### Where the gain lands, by competency

Correct counts out of 30 per cell:

| Competency | B1 | B2 | B3 | B4 | ASK | Δ vs B4 |
|---|---:|---:|---:|---:|---:|---:|
| knowledge-update | 4 | 17 | 20 | 21 | **29** | **+8** |
| multi-session | 1 | 4 | 6 | 17 | **19** | +2 |
| ss-assistant | 0 | 27 | 0 | 26 | **29** | +3 |
| ss-preference | 0 | 6 | 0 | 11 | **16** | +5 |
| ss-user | 2 | 23 | 12 | 23 | **25** | +2 |
| temporal-reasoning | 2 | 3 | 5 | 16 | **19** | +3 |
| **Total** | 9 | 80 | 43 | 114 | **137** | **+23** |

The controller leads on all six competencies, but the +23-item margin is not
spread evenly, and the concentration is the mechanistic evidence.
**Knowledge-update** is precisely the competency requiring recognition of a
superseding fact and replacement of the prior value — the decision the write
policy governs. It is where a governed write should help most and where it does
(29/30 against 21/30). **Single-session preference** is the second-largest gain
and also where the controller's abstention is most active (6 over-refusals),
consistent with the v7 error taxonomy in §8.1 attributing those failures to
retrieval and answer realisation rather than to the write policy.

Two competencies deserve a note the aggregate hides: B2 flat-vector reaches 27/30
on ss-assistant and 23/30 on ss-user — competitive with B4 — while collapsing to
**0/30** on ss-preference and 3/30 on temporal-reasoning. B3 recency collapses to
0/30 on both single-session competencies. Retrieval-only systems can answer
questions whose evidence sits in one retrievable place and fail completely when
the answer depends on a *maintained* state.

**Statistical honesty about the per-competency pattern.** Under Holm-corrected
paired exact McNemar tests across the six competencies, only knowledge-update
separates individually (p = 0.047); the other five have corrected p = 1.0. At
n = 30 per competency this is expected. The implication stated plainly: the
per-competency pattern is **descriptive evidence about where the effect
concentrates**, while the reliable inferential claim is the aggregate contrast
(p = 2.9 × 10⁻⁴). No single competency cell should be read as independently
established.

**Downstream cost in context.** Per-item end-to-end pipeline time is 809 s for
the governed controller and 966 s for naive overwrite, against 1.6–3.1 s for the
three retrieval-only baselines — roughly 320× against flat-vector retrieval,
buying 31.7 accuracy points. Answer-stage prompt tokens show the same ordering
(22,625 per item versus 14,227 and 3,629), but as the stage decomposition above
shows, that comparison understates the true gap by more than an order of
magnitude, because the retrieval-only baselines have no ingestion pipeline to
account for. Whether the exchange is worthwhile is a deployment question this
thesis does not adjudicate; the full accounting is reported so it is not hidden
behind the accuracy ordering.

### Write-decision behaviour (controller action log)

12,654 decisions across 3,547 sessions: **11,478 KEEP (90.7%)**, **779 ABSTAIN
(6.2%)**, **397 SUPERSEDE (3.1%)**. Candidate types: episodic_fact 9,857,
transient_pref 2,416, stable_pref 381. All 397 supersessions recorded both a
predecessor and a successor identifier; none of the 779 abstentions produced a
resulting record — the lineage and no-op invariants held on all 12,654
decisions. This distribution is what the design predicts on natural dialogue and
is very different from the balanced v4.3 diagnostic, which is why both
instruments are retained.

### Judge accounting

40 items resolved by deterministic guards (normalised match, no LLM call), 140
routed to the LLM judge, 2 scoring fallbacks, 0 model fallbacks. Nine items
received documented semantic-equivalence adjudications correcting judge scoring
errors, each with a written rationale and preserved pre-adjudication backup.

Two open provenance items, affecting no reported number: the homogeneity gate
flags a stale code/protocol hash for the evaluation launcher, and the manifest
was not written to a clean terminal status after a resume. Per-system integrity
checks (answer model, judge routing, fallback counts) pass with empty error and
warning lists.

## 9. What this evidence does not support

1. **No hidden comparator.** One configuration was authorised on the sealed
   split. Every baseline, ablation, and external-system contrast is development
   evidence on the split that selected the configuration.
2. **Development intervals are too narrow.** Component-cluster resampling is
   unavailable to the public scorer, so section 5 intervals are item bootstraps
   and the paired tests assume independence that does not hold within a
   component. Only contrasts with b/c splits of 98/6 or larger are relied upon;
   the 0.117 successor gain is the marginal case.
3. **The successor's 0.9611 is untested on any sealed split** and must not be
   read as an improvement over the 0.8481 hidden result — different splits under
   different exposure regimes.
4. **Annotation provenance is attested, not authenticated.** The builder
   validates records and hashes, not reviewer identity or duration. kappa = 1.0
   is equally consistent with a manual that is unambiguous by construction, so
   it certifies followability rather than construct validity.
5. **Abstention is not calibrated selection** (selective accuracy 0.8449 below
   overall 0.8481).
6. **One model family, one seed, temperature 0.** Intervals reflect item and
   component sampling, not run or model-family variance.
7. **No population, deployment-safety, or currency-cost claim.**
8. **The collection is synthetic, English-only, single-slot, single-step**, and
   has no selected public redistribution license.
