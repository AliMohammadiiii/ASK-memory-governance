# 1. Executive Summary

The recent literature reveals that long-term memory for LLM agents has evolved through three phases. Early work (2020–2022) focused on *static augmentation* of LLM context (e.g. Retrieval-Augmented Generation [RAG] or fixed memory logs). Representative systems include **MemoryBank**, which uses vector storage with forgetting curves, and **Generative Agents**, which store event logs and summaries. These approaches treat memory as passive storage without dynamic updates.

A second wave (2023–2025) introduced *memory lifecycle management*: systems that explicitly **add**, **update**, **merge**, or **delete** memory entries. Examples include **Memory-R1**, which uses RL-trained agents to perform ADD/UPDATE/DELETE/NOOP operations, and **RMM**, which merges relevant memory items after each session. **MemGPT** (2023) and **Mem0** (2025) adopt operating-system metaphors for multi-tier memory management (e.g. paging). **MemOS** defines MemCubes with versioning and provenances. These systems improve on pure retrieval by dynamically organizing stored knowledge, but they rarely address *when* to discard or override previous memories in the face of contradictions or user changes.

The current frontier (2025–2026) is *memory governance*: deciding when to **keep**, **supersede**, or **abstain** given new information. We found several related efforts. **FadeMem** (2026) explicitly detects memory conflicts: using an LLM to label new vs. existing memory as “compatible, contradictory, subsumes, or subsumed,” and then penalizing, suppressing, or fusing memories accordingly. **PAMU** (2025) models preference drift by tracking short-term vs long-term user preferences and triggering updates when shifts occur. Benchmarks like **LongMemEval** (2025) and **ES-MemEval** (2026) explicitly include *knowledge update* and *abstention* tasks, showing the community’s interest in correct memory revision and the dangers of hallucination. Work on **selective prediction** (e.g. RSCB-MC 2026) highlights the benefit of a “no-update” or **abstain** option when evidence is weak.

**Closest parallels to ASK** include systems that *partially* overlap on these axes. For example, RSCB-MC (2026) also treats memory injection as a risk-sensitive choice, explicitly allowing “no memory” or “abstain” to avoid wrong fixes. FadeMem’s LLM-based conflict resolution and PAMU’s drift detector similarly align with ASK’s motivation to handle contradictions and preference changes. However, none combine *typed memory*, *explicit version lineage*, *a transparent score-based update policy*, *an abstention action*, and *per-action evaluation* in one design. Graph-based memories (Zep/Graphiti) maintain validity timestamps, but do not frame update decisions in user-personalized terms.

**Novelty of ASK:** In the reviewed literature, no single prior system matches ASK’s combination of features. Systems have versioned or graph memories, and some employ abstention-like decisions, but explicit *supersession links*, *typed categories* (stable vs transient), and a *human-interpretable scorecard controller* appear unique to ASK. Similarly, action-level metrics for memory revision are absent outside HaluMem. Thus, the chief novelty claim is **not** that these elements individually are new, but that **ASK is the first to jointly integrate typed memory entries, explicit lineage tracking, a three-way update policy (keep/supersede/abstain), and transparent feature-based decision rules, validated by action-level evaluation**. This conjunctive claim seems defensible, though each component has precedents. We should be cautious not to overstate – for instance, supersession without abstention appears in RMM and versioning in MemOS, so the novelty is the *combination* and explicit design of abstention as a primary action.

# 2. Thesis Restatement

**Problem:** LLM-powered personal assistants accumulate user information across sessions, but users’ stated facts, preferences, or commitments can change, contradict, or be uncertain over time. The challenge is **memory governance**: when a new piece of user information arrives, should the system **Keep** the existing memory, **Supersede** it (overwrite with lineage tracking), or **Abstain** (refuse to commit due to ambiguity)? This goes beyond naive storage to decision-making about memory state.

**Method:** ASK implements a **typed external memory** with three categories (`stable_pref`, `transient_pref`, `episodic_fact`). Each entry has metadata (timestamps, evidence spans, confidence, lineage links). The **active controller (M3-W9.1)** uses five interpretable features (`c`: extraction confidence, `e`: evidence quality, `f`: linguistic marker burden, `r`: relation signal, `ρ`: type stability prior) to compute *supersede* and *abstain* scores. A threshold-based rule then picks Keep/Supersede/Abstain (see appendix for formulas). Notably, this is a rule-based (non-ML) policy intended to be transparent.

**Baselines:** We compare against (1) **No-memory** (LLM only), (2) **Flat-vector memory retrieval**, (3) **Recency-pruning** (forget oldest entries), and (4) **Naive overwrite** (always replace on conflict). Possibly also compare to an *LLM-controller* (learned policy) or relying solely on extended context.

**Evaluation:** ASK is assessed both end-to-end and at the action level. Downstream QA performance is measured via **LongMemEval-S** (a subset of LongMemEval) in typical assistant tasks. Critically, we also measure **revision correctness**: per-action precision/recall of Keep/Supersede/Abstain decisions using a hand-annotated subset (MGP-6). Additional metrics include over-/under-forgetting rates, stale-memory retrieval, and risk-coverage curves (commitment vs. correctness), following the paradigm of selective prediction.

**Intended Contribution:** The thesis claims a novel *combination* of features: a **typed, versioned memory** with explicit *supersession links*; an *abstain-as-action* design; a *transparent scorecard controller*; and an *action-level evaluation methodology*. We will argue that while elements of this appear in prior work, their integration in a single framework targeting **personalized LLM memory governance** is new.

# 3. Conceptual Evolution of the Field

The literature on LLM memory has progressed through three “waves”:

## 3.1. Wave 1 – Memory as Storage/Context Extension

**Central Idea:** Extend LLM context by retrieving relevant knowledge from an external source. Memory is passive: once written, it is not revised or deleted (unless via fixed forgetting rules). Key problems involve indexing and retrieval efficiency.

- **RAG and Vector Memories:** Retrieval-Augmented Generation (RAG) [Lewis et al. 2020] uses a text or vector store to fetch relevant docs. Extensions include continuous updating of the index but rarely handle contradictions. For example, *MemoryBank* stores user facts in a vector database and applies time-based decay (“Ebbinghaus forgetting”) to delete old memories. Memory is appended and forgotten by schedule; there is no active decision to overwrite or skip.

- **Simulation-based Agents:** *Generative Agents* (Park et al. 2023) hold a long log of events and “reflection” summaries. They retrieve by recency/relevance heuristics. There is no built-in mechanism to retract or question past memories. These systems focus on storing everything and retrieving what’s needed.

- **Multi-tier Memory Systems:** *MemGPT* (Packer et al. 2023) introduced an OS-inspired hierarchy (short-term vs. long-term) to extend context length, paging content like memory pages. It treats context extension as a resource management problem, but does not explicitly decide to forget or override specific facts.

**Limitations:** These approaches assume memory only grows (or decays by simple rules). They lack mechanisms to handle *changed or conflicting information*. The only “life cycle” is occasional summarization or pruning; they do not decide on a per-item basis whether a new input should rewrite an old one or be ignored.

## 3.2. Wave 2 – Memory Lifecycle Management

**Central Idea:** Memory is no longer a static log but an active resource. Systems define explicit operations (ADD, UPDATE, DELETE, NOOP) or maintenance strategies to keep memory relevant and efficient.

- **Explicit Update Operations:** *Memory-R1* (Yan et al. 2025) formulates memory management as an RL problem: a “Memory Manager” agent chooses among **ADD, UPDATE, DELETE, NOOP** for each candidate memory. This explicitly allows revision (UPDATE) and removal (DELETE). However, the learned policy is opaque, and there is no *explicit abstain* action: UPDATE is always performed if chosen (no threshold for uncertainty).

- **Merge/Add Frameworks:** *Reflective Memory Management (RMM)* (Luo et al. 2025) introduces “prospective reflection” at session end: new memories are summarized and then **merged** into existing ones if they overlap topics, otherwise **added**. The rule is straightforward: if a new memory is relevant to a past topic, combine them; if not, append. This prevents duplication but has no facility for *contradictions* or uncertainty.

- **Agentic Memory Systems:** *A-MEM* (Xu et al. 2025) uses an agentic process: new memory notes are structured (with keywords/tags), then the system automatically links them to semantically similar prior memories and updates those old memories’ content (“memory evolution”). It defines “ADD, UPDATE, DELETE” as high-level operations. Like RMM, it merges related entries, but does not introduce *abstention*, the agent always integrates new info by either updating or linking.

- **Hierarchical Memories (MemOS, Mem0):** *MemOS* (Li et al. 2025) and *Mem0* (Chhikara et al. 2025) introduce more sophisticated memory architectures. MemOS organizes “MemCubes” with versioning metadata; data flows through short- and long-term storage, and memory entries can be migrated or fused. Mem0 uses graph representations and dynamic consolidation. These systems focus on *efficiency and structure* of storage, not on per-item governance. They still lack explicit **skip** or **abstain** choices – they will consolidate whatever is stored.

- **Forgetting and Decay:** Some lifecycle schemes emulate human forgetting. *MemoryBank* decays memories over time. *FadeMem* (Wei et al. 2026), although more of Wave 3, also uses decay to suppress contradictory old memories. The idea is to “forget” less relevant or replaced facts, but typical systems do this uniformly, not based on evidence from new input.

**Limitations:** Wave 2 systems broaden memory operations but often *lack explicit criteria* for when to apply them. For example, RMM merges by similarity; Memory-R1 learns policies but is black-box. None provide *explainable*, fine-grained controls for ambiguity: new inputs are always applied in some way. Contradictory updates are not specially treated (e.g., conflicting facts may just be merged). And again, **abstention** is not a defined option, memory is always updated unless some heuristic says “delete”.

## 3.3. Wave 3 – Memory Governance

**Central Idea:** Treat memory updates as **decision problems** with safety and reliability in mind. Emphasize correctness of updates, versioning, and the option to *decline* uncertain updates.

- **Conflict Detection and Revision:** *FadeMem* (Wei et al. 2026) explicitly handles contradictions: new entries trigger LLM-based classification of the pair (new vs old) into *Compatible, Contradictory, Subsumes, Subsumed*. Then rules apply: contradictory old memory is decayed (older info suppressed), subsumed facts are merged, etc. This is a clear step toward governance: the system decides *how* to revise or remove memory in light of new input. However, it does not allow “abstaining” – if a conflict is detected, one entry is always modified or suppressed.

- **Preference Drift and Update Policies:** *PAMU* (Sun et al. 2025) focuses on evolving user preferences. It computes short- vs. long-term preference signals and triggers memory updates only when a statistically significant shift occurs. Implicitly, if no drift is detected, the system **keeps** the old preference. This is a form of *selective update*: it embodies a conservative (abstain-like) stance when evidence is weak. However, PAMU is specifically about preferences and still does not annotate lineage or evidence spans.

- **Governance Frameworks:** Zhu et al. (2026) present **SSGM**, a conceptual framework for *governed memory*. They emphasize the “stability-plasticity” trade-off and identify risks like memory poisoning or drift. SSGM proposes modular checks (consistency verification, decay modeling) before committing memory. While not an implemented system, it underscores the need for controlled update policies. It also reviews existing approaches: e.g., noting Memory-R1’s RL strategy and Mem0’s consolidation, but arguing that these lack governance safeguards.

- **Selective & Abstention-Aware Controllers:** In other domains, researchers have begun integrating **abstention** or **safety thresholds**. For instance, in coding agents, *RSCB-MC* (İscan et al. 2026) uses a contextual bandit to decide whether to apply a past fix to a current error. Actions include “**no memory**” or “ask for feedback”, and the policy is risk-sensitive (false positives are heavily penalized, so abstention is favored when unsure). This illustrates the value of an explicit “abstain/no-op” decision. By analogy, ASK’s *Abstain* maps to this notion: the agent can explicitly *decline* to store a new fact if evidence is low or ambiguous.

- **Action-Level Evaluation:** Recognizing the limitations of end-to-end metrics, recent benchmarks (LongMemEval, HaluMem, etc.) and proposed metrics focus on *the correctness of each memory action*. For example, the HaluMem benchmarkreveals that hallucinations often arise at the memory writing stage. This shift in evaluation highlights that memory governance is about *each memory operation’s quality*, not just final QA accuracy.

**Limitations:** Although these governance-oriented efforts take steps toward principled memory updates, none have implemented the full ASK design. For example, no prior system explicitly provides a *third option (“abstain”) as a declared action among keep/supersede*. Supersession and versioning have appeared (e.g. MemOS’s MemCube version tags, Graphiti’s validity windows) but typically as afterthoughts. Most systems still either merge/update deterministically or learn policies without interpretability. ASK’s emphasis on transparency and evidence spans is novel: existing works rarely expose *why* a decision was made (e.g., FadeMem uses an LLM classifier without human-readable criteria). In summary, *memory governance* is emerging as a topic, but ASK pushes it further by formalizing *when to update vs. keep vs. defer*, with explainable features and lineage.

# 4. Detailed Related Work by Cluster

### 4.1 Retrieval and External Memory

- **Retrieval-Augmented Generation (RAG):** Classic RAG (Lewis et al. 2020) uses a static retriever over a knowledge base. It improves factuality but assumes the KB is updated externally. It doesn’t handle *user-specific memory* or dynamic updates. Modern agents often embed RAG as the Retrieval/Reading stages of a pipeline.

- **MemoryBank (Zhong et al. 2024):** MemoryBank augments chatbots with a memory bank that *summarizes and stores observations*. It applies an “Ebbinghaus forgetting” schedule: each memory’s importance decays over time, and frequently recalled items are reinforced. This allows the agent to forget old info organically. However, MemoryBank treats new memory as always added; if contradictions occur, they are not explicitly resolved. MemoryBank’s update mechanism is fixed (time-based), not evidence-driven.

- **Generative Agents (Park et al. 2023):** This system records detailed user experiences. The agent stores “narrative memories” (events, observations) and periodically synthesizes reflections. Retrieval is based on recency and importance. There is *no mechanism* to override or reject stored memories: everything is retained (though older memories can become less relevant). Its memory is purely additive and summary-oriented, making it a good contextual store but not a governance system.

- **MemGPT (Packer et al. 2023):** Proposes an OS-like architecture for LLMs, with multiple memory tiers and a Memory Pager. It continuously saves dialogue “pages” and swaps them between RAM and long-term storage based on heuristics. It thus *extends context* beyond the LLM’s window. However, it has no semantics for user-specific facts or their validity; it simply ensures relevant conversation context is available. It does not address contradictions or preferences.

- **Vector Memory Stores:** Systems that keep memory as vector embeddings (RAG-style) allow fast retrieval of similar contexts. These include basic RAG extensions or tools like RedisVector, Chroma, etc. They are storage/retrieval tools, not decision-makers. There is no built-in logic for updating or deleting specific items beyond user calls; any “update” is just writing a new vector.

- **MemoryBank-like Hybrids:** Other works (e.g. some Generative Agent follow-ups) use summaries and indexing, but again lack action-based updates.

**Relevance to ASK:** These retrieval-based systems establish the baseline that memory can exist externally. They lack the notion of *memory operations* beyond “store and retrieve”. ASK moves beyond these by treating memory writes as decisions. In particular, ASK’s abstain action has no counterpart here, and even the supersede decision goes beyond simple retrieval by adding explicit lineage.

### 4.2 Memory Lifecycle Systems

- **Mem0 (Chhikara et al. 2025):** An industry-oriented system that graphs interactions and builds a memory of “entities, documents, facts” with timestamps. It automatically consolidates relevant information and prunes noise. Mem0 emphasizes multi-session context and uses *graph structures* to represent memory. It was evaluated on the LoCoMo and LongMemEval benchmarks (achieving ~95% in some tasks). Mem0 shares with ASK the idea of structured memory, but it does not explicitly define a transparent decision rule for updating an existing memory entry. It also does not have an “abstain” mode – it tends to incorporate new info by appending or merging without a refusal option.

- **MemOS (Li et al. 2025):** As described above, MemOS introduces MemCubes that track provenance and version history. When new information arrives, MemOS can “compose, migrate, and fuse” MemCubes. For example, facts can be fused across cubes. This effectively supersedes old facts by merging them, and it preserves provenance links (a similarity to ASK’s supersession lineage). MemOS’s modules for “scheduling and evolution” suggest it could avoid unwanted overwrites, but details of actual update logic are not disclosed in open sources. The focus is on system architecture rather than inference rules.

- **A-MEM (Xu et al. 2025):** This agentic memory system automatically organizes new memories and updates old ones. It generates structured notes for each memory (context, keywords, etc.), and then *linking*: each new note triggers connecting it to similar existing notes (forming a Zettelkasten graph). It also “evolves” existing notes by adding new context. Essentially, a new memory may be appended or merged depending on relevance. There is no explicit abstention. A-MEM’s policy is implicit in its algorithm: always integrate new info. Its contributions are more on knowledge representation and linking, less on update decision-making.

- **RMM (Luo et al. 2025):** We saw that RMM extracts session summaries and then either merges them or adds them to memory. Concretely, after summarizing a session, the agent *retrieves* similar memory slots and if similarity exceeds a threshold, *merges* the new info into the old; otherwise, it *adds* a new slot. This is an update rule: it avoids duplicate or redundant memories. However, RMM does not handle contradictory info specially, nor can it choose to “ignore” a new summary. It assumes each summary should either combine with something or become new. RMM’s controller is an LLM summarizer + a similarity threshold – it’s partly learned (the retriever) but the merge/add decision is deterministic.

- **Add/Update/Delete/NoOp Paradigm:** Memory-R1 introduced the idea of treating memory management as an action set. It is one of few to have a “NOOP” (keep) action. ASK’s “Keep” is analogous to NOOP. Memory-R1’s novelty was learning this via RL, but ASK uses a fixed feature-based policy. RMM’s “merge” vs “add” is similar to UPDATE vs ADD (merging into an existing entry vs creating a new one). However, RMM lacks a NOOP: it always updates memory at session end.

- **MemoryBank (again):** Even though MemoryBank was mentioned earlier as retrieval, it also has an *update* component: it periodically **refines** memories by consolidating them into summaries and discarding details. But this is not in response to specific new inputs; it's a schedule (like every day compress logs). ASK’s approach is more dynamic and evidence-driven.

**Relevance to ASK:** Wave 2 systems introduce many operations analogous to Keep/Supersede, but usually without an interpretability layer or abstention. For instance, Memory-R1’s UPDATE is like ASK’s Supersede but without tracking old vs new or a threshold to withhold. RMM’s merge uses a crude similarity instead of multi-feature scoring. ASK’s typed memory (stable/transient) has no direct analog here, though MemOS’s MemCubes support heterogeneous memory. Overall, ASK’s **novelty claim** relative to these is that it explicitly names and controls Keep vs Supersede vs Abstain, whereas others implicitly encode decisions in complex logic.

### 4.3 Revision, Contradiction, and Drift

- **FadeMem (Wei et al. 2026)**: This is one of the first systems explicitly targeting *contradictory and redundant memory*. When a new fact is stored, FadeMem retrieves similar old memories and has the LLM classify their relation. Depending on the label, it either decays old memories (if Contradictory), reduces redundancy (Compatible), or fuses them (Subsumes/Subsumed). This yields an adaptive forgetting mechanism: contradictory memories are actively suppressed. FadeMem was tested on Multi-Session Chat and LoCoMo, showing it resolves conflicts that naive methods would get wrong. Its supersession is implicit (new facts override old via suppression), but it does not log a lineage nor allow “no action”: it always modifies memory if conflict is detected.

- **PAMU (Sun et al. 2025)**: Focuses on *preferences*. It extracts a user’s preference vector from recent dialogue and maintains a long-term EMA version. When the deviation between short-term and EMA exceeds a threshold, it *updates* the memory of preference (a “refine” operation). If not, it implicitly “keeps” the old preference. Thus PAMU has a simple two-state memory (short/long) and does something akin to Supersede (when shift is high) or Keep (when stable). It is explicitly designed for drift detection and is *interpretable*. However, it does not deal with generic facts or contradictions – only preference changes. No abstain action is needed since decision to update is already about weak vs strong signal.

- **MirrorNet/KEEM-like Datasets:** The KEEM dataset (Kang et al. 2026) was created to encourage systems that generate “integrative” memory updates combining old and new information. KEEM data includes emotional context and causality. The authors note that *naive accumulation leads to conflicts*, suggesting the need for conflict-aware updates. KEEM itself isn’t a model, but it highlights the problem: current models often just append (“accumulate”) and create incoherence.

- **Conflict- and Contradiction-Detection:** Apart from FadeMem, some works have looked at identifying contradictions in user input (e.g., in persona-based chatbots). However, they seldom integrate this into memory update logic. ES-MemEval explicitly tests *Conflict Detection* (CD) as a memory capability, underscoring its importance. But few systems automatically enforce consistency.

- **Other Updates:** Some graph-based personal memory approaches (not explicitly named ASK) allow “redaction” or “overwriting” – e.g., an invalidated fact might be marked obsolete. But these are usually application-specific (like knowledge base revision) rather than general LLM agent memories.

**Relevance to ASK:** These revision-focused works align closely with ASK’s motivations. FadeMem’s handling of contradictory input is very similar to ASK’s goal of superseding outdated memory, though FadeMem’s rules are biologically inspired (exponential decay) and use an LLM classifier. ASK’s approach is simpler and transparent. PAMU’s change detection is akin to ASK’s confidence/evidence scoring for preferences. In both, a key idea is *not* to blindly overwrite unless justified. However, none of these include an *abstain* choice: if FadeMem can’t reconcile two memories, it still makes a change. ASK’s abstain is unique. Also, ASK logs explicit lineage (“supersedes” links) for transparency, whereas FadeMem simply merges or deletes. In sum, ASK overlaps with prior work on *how* to handle conflict and drift, but its emphasis on refraining from action when appropriate appears novel.

### 4.4 Provenance, Versioning, and Temporal Graph Memory

- **Zep/Graphiti (2025)**: This is a cutting-edge approach that models memory as a **temporal graph**. Each fact is a node with “valid-from” and “valid-until” timestamps (i.e. a versioned fact). For example, a fact might be true from Jan–June, then superseded by a new value. Graphiti records *episodes* of events, linking them to derived facts. The key is that old facts are *not deleted*; they are merely marked outdated. This means Zep inherently preserves a supersession lineage: one can query “What was true at time T?” or “what has changed?” It directly addresses versioning and provenance. In ASK terms, this is similar to having an explicit “supersedes” pointer and validity window. However, Zep’s updates are typically driven by external data (e.g., parsed events), not by a learned policy; it doesn’t make an “abstain” decision but rather always pushes new facts with updated validity. It also doesn’t resolve contradictions semantically – it relies on temporal validity.

- **MemOS (again)**: MemOS’s MemCubes are annotated with version tags and provenance metadata. It supports combining memory entries over time. This is similar in spirit: any change can create a new version linked to prior ones. MemOS thus provides lineage, though the decision process behind forming new versions is not detailed. It’s more about system design. ASK’s lineage (supersedes links) is much like MemCubes’ versioning.

- **Temporal Knowledge Graphs:** There is a line of work on AI knowledge graphs that handle time (e.g., TKGs) and on versioned document stores (e.g., temporal databases). Some LLM memory systems have drawn on these ideas (e.g., TEMP based memories). These systems allow queries about “prior beliefs,” but again, do not usually address *update policies*. They illustrate the feasibility of non-lossy memory.

- **Audit Trails:** Some proposals for LLM agents have suggested keeping an “audit log” of edits (especially for safety-critical use). This aligns with ASK’s logging: every memory update is recorded with evidence. We did not find a specific published system that does all of ASK’s logging (confidence, spans, etc.), but the concept of “evidence spans” appears in RAG contexts (like using retrieved passages as justification).

**Relevance to ASK:** Zep and MemOS show that explicit versioning and provenance are beneficial and increasingly common. ASK is aligned with this trend but restricts its scope to the personal-memory domain. The novelty is that ASK treats supersession as an *action* with its own logic. Existing systems often version facts implicitly (e.g. Graphiti timestamping) without an active choice to supersede. Also, ASK’s evidence spans (the dialogue text that supported an update) are akin to provenance links, strengthening explainability.

### 4.5 Personalized Memory and Preference Tracking Benchmarks

- **PrefEval (Zhao et al. 2025)**: PrefEval is a large-scale benchmark (ICLR 2025) testing how well LLMs follow user preferences revealed in conversation. It has 3,000 preference–query pairs, mixing explicit and implicit preferences. The study found that without fine-tuning, even state-of-the-art LLMs fail badly on multi-turn preference following. They try methods like RAG and improved prompting, but performance stays low. PrefEval highlights the need for better memory of user tastes, but it doesn’t prescribe how memory should be updated – it just measures whether LLMs can use given information.

- **PersonaMem-v2 (Jiang et al. 2025)**: A synthetic personalization dataset (30k+ tokens per conversation) with 20k implicit preferences. They also explore an **agentic memory system** which stores a growing memory summary for the user. They show that training a model with RL fine-tuning on this data improves personalization accuracy, and that using a small memory buffer (2k tokens) with an agentic memory improves over using the entire 32k context. Again, the focus is on evaluating personalization impact, not on policy for updating memory items.

- **RealPref (Guo et al. 2026)**: Similar in spirit to PrefEval, but emphasizing *“realistic”* multi-session interactions. RealPref has 100 users and 1300 preferences across long dialogues. It categorizes preference expressions from explicit to implicit and tests LLMs on multiple-choice, T/F, and open tasks. It shows performance drops as context length grows and preference expression becomes subtle. Like PrefEval, RealPref is diagnostic: it reveals that LLMs struggle to generalize preferences, but doesn’t offer a memory-update mechanism.

- **ALPBench (Ren et al. 2026)**: This benchmark for personalized recommendation reframes the task as predicting user attribute interests from long histories. It’s less directly about dialogue memory and more about static user-item data (footage). Its focus is on evaluating how well an LLM can model stable vs transient interests. It indirectly relates to memory drift, but is in the recommendation domain.

- **LikeBench (Rahman et al. 2025)**: This proposed benchmark measures *likability* in multi-session chat. It decomposes user satisfaction into aspects (emotional adaptation, formality, etc.). Interestingly, it finds that *memory accuracy alone is not enough* for likability. For example, one model (DeepSeek R1) with lower memory recall outperformed another with higher recall in user satisfaction. This suggests that simply recalling facts (like a static memory store) doesn’t guarantee good personalization outcomes.

**Relevance to ASK:** These benchmarks show the state of evaluation for personalization and memory. PrefEval and RealPref emphasize the difficulty of *using* memory correctly; they implicitly support ASK’s goal of improved memory governance for preferences. However, they don’t include an abstention action or lineage. LikeBench’s insight that recall≠likability suggests that how memory is used (or revised) is crucial. None of these benchmarks test the kind of memory-update actions ASK targets, but they underscore why careful update policies matter. ASK’s use of LongMemEval-S for QA fits with this theme, but ASK’s own MGP-6 (manual revision tasks) is novel.

### 4.6 Long-Term Memory Benchmarks

- **LongMemEval (Wu et al. 2025)**: A broad benchmark suite for long-term memory in assistants. It contains 500 QA problems across realistic chat logs spanning many sessions. Crucially, it includes tasks for knowledge update (requiring models to incorporate new user info and override old), and abstention (knowing when a question is unanswerable). The design explicitly probes “knowledge supersession/overwrite”. It showed that vanilla models drop 30–60% on these tasks. LongMemEval is precisely the kind of evaluation ASK uses downstream. It reveals that without proper memory handling, QA fails on updates, supporting ASK’s motivation.

- **LoCoMo (Maharana et al. 2024)**: A synthetic long-dialog dataset with 300 turns over ~35 sessions (up to 9K tokens). Tasks include QA, event graph summarization, and multimodal dialogue generation. It highlights temporal and multi-hop reasoning. LoCoMo is used by Mem0 and others to test long-memory architectures. It does not focus on preference or contradictions, but on “very long conversations”. It provides a scale that ASK’s baselines could be tested on.

- **ES-MemEval (Chen et al. 2026)**: Designed for *emotional support* dialogues, this benchmark explicitly includes **Conflict Detection** and **Abstention** among its memory capabilities. It tests information extraction, temporal reasoning, but also whether agents can detect contradictions (e.g. a user stating opposite facts across sessions) and whether they refrain from answering when lacking evidence. This is directly relevant to ASK: it formalizes exactly the tasks of identifying stale/contradictory memory and abstaining on insufficient info. ES-MemEval emphasizes the necessity of these skills in practice.

- **ES-MemEval** also includes metrics for conflict detection and abstention as separate tasks (see Fig.5). This shows the community is beginning to value the same qualities that ASK encodes.

- **HaluMem (Chen et al. 2025)**: Not a benchmark for memory *tasks*, but a benchmark for *hallucination*. It defines memory *extraction*, *update*, and *QA* stages, each with test questions. Its finding that “existing memory systems tend to generate and accumulate hallucinations during extraction and updating” suggests that current memory pipelines are not well governed. HaluMem underscores the need for “interpretable and constrained memory operations” to avoid erroneous updates. This is a direct call for the kind of cautious update policy (with abstention) that ASK implements.

- **Other Benchmarks:** Additional benchmarks (LongMemEval’s variants, LEM memory tasks) exist, but the key ones are above. The ALPBench and PrefEval in the previous section address personalization; LongMemEval and ES-MemEval address memory update and abstention; LoCoMo and BEAM test scale. We have covered the main relevant ones.

**Relevance to ASK:** Benchmarks influence the design of systems. The presence of tasks for knowledge update, temporal reasoning, and abstention in LongMemEval and ES-MemEval directly validates ASK’s focus. That is, ASK targets high scores on these tasks, acknowledging that QA accuracy alone is insufficient. Importantly, these benchmarks measure end-to-end performance; ASK complements them with per-action metrics. Also, HaluMem’s findings support ASK’s claim that one must control each operation (to avoid hallucinations), so ASK’s action-level evaluation is on-point.

### 4.7 Long-Context Limitations

- **RULER (Hsieh et al. 2024)**: This synthetic benchmark extends the “needle-in-a-haystack” test of context. RULER adds *multi-hop tracing* and *aggregation* tasks. It shows that even when models have long context windows (32K tokens), performance drops sharply with length. It finds that models claiming 32K-context often fail around that length. RULER highlights that context compression and retrieval alone are not enough for “comprehensive long-context understanding”.

- **ONERULER (Kim et al. 2025)**: Multilingual version of RULER over 26 languages. It confirms RULER’s findings across languages and adds the twist that different languages fare differently at scale. It also tests scenarios where the context has no answer (“needle missing”) and how well models detect that absence. This underscores that models struggle with long contexts in general, making memory systems (like ASK’s external memory) necessary for extended reasoning.

- **BEAM (Tavakoli et al. 2025)**: A very large-scale benchmark (up to 10 million token conversations). It reveals that *even huge context windows are inadequate* for realistic dialogue. The authors note that earlier benchmarks often lacked narrative coherence, whereas BEAM’s long dialogues are coherent, and still models fail. BEAM also introduced **LIGHT**, a hybrid memory architecture, and found it improved performance slightly. Importantly, they state existing benchmarks “overlook other critical memory abilities such as contradiction resolution, evolving information” – exactly the gap ASK addresses. BEAM thus motivates the need for explicit memory beyond context.

- **“Lost in the Middle” (Tran et al. 2023)**: Empirically, LLMs often suffer from positional bias – they remember beginnings and ends of context better than the middle. This principle justifies having an external memory store rather than relying on vanilla context. ASK’s use of a memory store and retrieval (chain-of-note strategies) combats this limitation.

**Relevance to ASK:** The lesson from these works is that merely feeding more context (longer windows or better retrieval) is not enough to solve long-term memory tasks. Instead, structured memory storage (like ASK’s external memory) is required. ASK’s baselines include “flat-vector memory” and “long-context LLMs”, and we expect RULER/BEAM findings to hold: they will underperform ASK’s specialized memory. The benchmarks also remind us to explicitly mention these limitations: e.g. we will argue that ASK’s design is necessary because context alone fails in multi-session settings.

### 4.8 Abstention, Selective Prediction, and Uncertainty

- **Selective Prediction:** In traditional ML, the concept of **selective classification** (Chow’s rule) or deferral is well-studied: a model can abstain if confidence is low, trading coverage for accuracy. Recent LLM work echoes this (e.g. “Knowing When to Abstain” in medical LLMs). While we found no LLM-specific papers on memory update abstention, these ideas apply directly.

- **RSCB-MC (Iscan et al. 2026)**: Mentioned above, RSCB treats memory retrieval as a risk-sensitive decision problem. Its action space includes **“no memory”** and **“abstain (ask feedback)”**, explicitly modeling the abstention concept. It shows that punishing unsafe memory use yields better reliability. This is the closest to ASK’s abstain: in coding memory, it preferred non-injection when uncertain.

- **RPEval (Feng et al. 2026)**: RPEval’s *RP-Reasoner* module essentially decides *which* stored memories to use at answer time (noisy supervision usage). It is a form of selective retrieval/commitment. Though it addresses retrieval rather than storage, it demonstrates that smart selection (or refusal to use certain memories) improves outcomes.

- **Abstention in QA:** Some memory benchmarks (e.g., LongMemEval, ES-MemEval) include *abstention* as a task: the model must detect when a question cannot be answered from memory. While this is output-level abstention, it reflects the same principle: the system should *withhold* rather than hallucinate. By analogy, ASK’s *Abstain* means “do not store this uncertain update,” a form of knowledge-level abstention.

- **Uncertainty & Calibration:** Several works (e.g. Agrawal et al. 2023) examine calibrating LLM confidence scores. A well-calibrated model can gauge when it “knows” vs “doesn’t know”. ASK uses features (like extraction confidence `c`) that are related: if confidence is low, `S_abs` will trigger Abstain. This is akin to deferring update in low-certainty cases, inspired by selective classification intuition.

**Relevance to ASK:** While pure abstention in memory updates is not well-covered in prior LLM research, related literature supports its inclusion. RSCB-MC provides direct evidence that no-memory/abstain can be essential. General selective classification theory shows that precision/coverage trade-offs can be controlled via thresholds. ASK essentially implements a selective-memory mechanism: if evidence is ambiguous, do nothing. We will cite these analogues to justify ASK’s Abstain as a sensible, if novel, action. (In novelty analysis, we note that no earlier personal-LM memory system formally defines “abstain” as part of its policy.)

# 6. Direct Nearest-Neighbor Analysis

We identify the 6 systems closest to ASK (in terms of memory governance):

### Work: **RSCB-MC (İscan et al., 2026)**
**Overlap with ASK:** Both treat memory update as a decision problem with an explicit “no memory/abstain” action. RSCB-MC uses a feature-based controller (contextual bandit) with risk penalties, punishing unsafe memory use more than misses. It, like ASK, keeps *no-memory* as a first-class safety move.
**Difference from ASK:** RSCB-MC is for coding agents (debug fixes) and focuses on *retrieval/injection*, not long-term user memory. Its action space (no memory, inject, ask) maps roughly to ASK’s (keep, supersede, abstain), but RSCB-MC’s “inject top fix” is not symmetric to ASK’s write policy. Its controller is learned (bandit RL) rather than fixed, and it uses domain-specific features. ASK is manually designed and transparent.
**Implication for novelty:** RSCB-MC demonstrates the *value* of an abstain option in memory use, supporting ASK’s design. However, RSCB-MC’s context and methodology differ, so it does not preempt ASK.
**Risk to ASK claim:** *Low.* RSCB-MC shows abstention can work but does not cover personal memory or supersession lineage. It actually strengthens the case that ASK’s abstention is sensible.

### Work: **FadeMem (Wei et al., 2026)**
**Overlap with ASK:** FadeMem explicitly handles contradictory and redundant memory. It classifies new vs. old memory pairs and then modifies memory (decay old, fuse, etc.) based on rules. This is similar to ASK’s goal of *superseding outdated memory*. It uses LLM reasoning to detect conflicts.
**Difference from ASK:** FadeMem’s actions (suppress/fuse) are more complex and continuous than ASK’s discrete Keep/Supersede. It does not include an abstention concept; every conflict yields some action. It also does not maintain explicit lineage – when memories merge, the old identity is subsumed. ASK, by contrast, logs supersession links. Also, FadeMem’s policy is implicit (rules plus LLM classifier), not a transparent score model.
**Implication for novelty:** FadeMem’s presence is a threat only in that it also addresses conflicts, but it lacks abstention and explicit lineage, so ASK still covers new ground. It’s a *contemporaneous strong baseline* for revision quality.
**Risk to ASK claim:** *Medium.* FadeMem is very similar in intent (memory conflict resolution) but different in mechanisms. ASK should compare to FadeMem in experiments. It weakens any claim of “first to handle contradiction,” but ASK’s abstain feature remains unique.

### Work: **MemOS (Li et al., 2025)**
**Overlap with ASK:** MemOS brings versioning and provenance to LLM memory through MemCubes. It maintains multiple memory levels and allows facts to be updated over time, including metadata on when and why. This aligns with ASK’s goals of traceable supersession.
**Difference from ASK:** MemOS is a full system architecture; it doesn’t specify a particular Keep/Supersede/Abstain logic or thresholds. Its memory operations (compose/migrate/fuse) are not directly mapped to ASK’s discrete actions. It is not personalized (it’s more general knowledge storage). Also, MemOS’s design is complex and not agent-specific.
**Implication for novelty:** MemOS shows that versioning memory with provenance is feasible. ASK’s claim of novelty in lineage should be tempered by MemOS’s similar idea. However, ASK’s setting (personal memories, structured action log) is still distinct.
**Risk to ASK claim:** *Medium.* MemOS could be cited as precedence for versioning, so ASK should not claim versioning as entirely new. The combination of versioning *with* a feature-based update rule (and abstain) is the novelty.

### Work: **PAMU (Sun et al., 2025)**
**Overlap with ASK:** PAMU addresses *preference drift* by detecting when a long-term preference should be updated. This mirrors ASK’s goal in the stable/transient preference domain. PAMU’s architecture (short-term vs EMA) is interpretable, and it explicitly says “update only if signal strong”.
**Difference from ASK:** PAMU is specialized to preference vectors and uses sliding windows and EMA. It lacks ASK’s generality and does not consider evidence spans or confidence beyond statistical shift. It has no “abstain” label (keeping the old preference is just “no update”). PAMU also doesn’t create lineage links or handle arbitrary facts.
**Implication for novelty:** PAMU shows the importance of refusing updates without significant evidence. This supports ASK’s design. But it is domain-specific. ASK’s method could incorporate a similar drift detector for preferences, but ASK is broader.
**Risk to ASK claim:** *Low.* PAMU is conceptually aligned but limited to preferences. It reinforces ASK’s rationale.

### Work: **RMM (Luo et al., 2025)**
**Overlap with ASK:** RMM’s memory merging captures a form of revision: if new info is relevant to an old memory, it merges (effectively updating the fact). Otherwise it adds new memory. This is superficially similar to deciding Keep vs. Supersede.
**Difference from ASK:** RMM has no abstain option (it always does something), and no explicit evidence quality weighting – just a similarity threshold. RMM does not log which memory was replaced or track time validity. Its policy is also not transparent to the user (it’s a static algorithm with thresholds).
**Implication for novelty:** RMM partially covers the idea of merging overlapping memories, but is narrower. It suggests ASK’s merging idea has parallels, so ASK should note RMM. However, RMM lacks ASK’s abstention and multi-feature decision.
**Risk to ASK claim:** *Low.* RMM simply illustrates merging vs adding; ASK’s fine-grained decision-making is more advanced.

### Work: **Graphiti/Zep (B. Rasmussen et al., 2025)**
**Overlap with ASK:** Graphiti/Zep provides a temporal knowledge graph for agents, including validity windows for facts and episodes as provenance. It explicitly represents supersession: facts have time spans and are never truly deleted. This solves a similar problem: tracking when a memory was superseded.
**Difference from ASK:** Zep does not decide *when* to supersede; it simply *records* it (e.g. “fact X valid until t, superseded by fact Y at t”). Its update logic comes from whatever feeds it (maybe manual or detection, unclear). Zep also does not include abstention or selective commit – it just logs data.
**Implication for novelty:** Zep validates the idea of temporal versioning. ASK’s lineage claims must acknowledge Zep. However, Zep is more a backend; ASK focuses on the agent-level decision to write or not.
**Risk to ASK claim:** *Moderate.* Zep’s existence means versioning provenance is not novel, but ASK’s approach to it in a personal agent is different. Must not overclaim that versioning is unique.

### Work: **LongMemEval (Wu et al., 2025)**
**Overlap with ASK:** LongMemEval defines tasks (information extraction, updates, abstention) that match ASK’s evaluation targets. ASK actually uses a subset of LongMemEval for QA tests.
**Difference from ASK:** LongMemEval is an evaluation suite, not an agent. It doesn’t propose a memory mechanism or operations. It does include “knowledge updates” and “abstention” as categories, which shows that ASK’s objectives are aligned with community benchmarks.
**Implication for novelty:** As a benchmark, LongMemEval is not competing with ASK’s technical approach. But ASK should note that LongMemEval (and ES-MemEval) provide relevant evaluation tasks that are dissimilar from simple QA metrics.
**Risk to ASK claim:** *None.* LongMemEval is not a system. It actually highlights ASK’s gap: we need better memory revision than QA accuracy.

# 7. Novelty and Gap Assessment

We evaluate candidate novelty claims for ASK:

1. **“ASK introduces memory operations Keep/Supersede/Abstain.”**
   - *Assessment:* **Weak.** Many systems have had analogous operations, though under different names. Memory-R1 had ADD/UPDATE/DELETE/NOOP (NOOP ≈ Keep); RMM had ADD/MERGE; RSCB-MC had “no memory/abstain”. The idea of an abstain action in memory updates is new for LLM agents (to our knowledge), but not entirely unprecedented in broader ML. Claiming ASK “introduced” these names is overselling – they are intuitive concepts. Instead say: “We formalize a three-way update policy (Keep, Supersede, Abstain) in the context of personal memory.”
   - *Support:* ASK’s formalization of abstain as primary is not seen in cited systems.
   - *Threats:* RSCB-MC explicitly uses “NoMemory/Abstain”, and RMM had merge/add.
   - *Safer wording:* “ASK explicitly frames memory revision as a ternary decision problem (keep existing fact, supersede it, or abstain from updating) – a triad not jointly named and studied in prior agent-memory work.”

2. **“ASK introduces versioned memory lineage for personalized LLM memory.”**
   - *Assessment:* **Moderate.** Temporal graphs (Zep) and MemOS's MemCubes already use versioning and provenance. So lineage per se is not novel. However, few personal assistant systems do this. It's safer to claim we apply versioning to *personal memory items*.
   - *Support:* Zep does exactly validity windows, and MemOS does versioning.
   - *Threats:* MemOS, Zep.
   - *Safer wording:* “While versioned facts and provenance have appeared in prior memory architectures (e.g. Zep/Graphiti), ASK is novel in applying explicit supersession links within a personalized memory controller.”

3. **“ASK introduces abstention as a first-class memory-write action.”**
   - *Assessment:* **Strong.** Aside from RSCB-MC (coding domain) and the conceptual idea in SSGM, no published personal-memory system defines abstain as an action. ASK is among the first (perhaps the first in this context) to make abstention a primary option in memory update. We can claim novelty of making *explicit* the idea of “not writing when evidence is low”.
   - *Support:* Lack of prior system that labels “Abstain” as memory action in citations. RSCB-MC is similar but in a different context.
   - *Threats:* RSCB-MC comes closest (though it’s retrieval in coding). Possibly “partial abstention” in PAMU (choosing not to update) – but that’s not labeled.
   - *Verdict:* **Strong**, but qualify by citing RSCB-MC as analogous work.
   - *Safer wording:* “ASK is, to our knowledge, the first to formalize **abstention (refusal to update)** as a primary memory action in personalized LLM assistants.”

4. **“ASK introduces a transparent feature-based controller for memory revision.”**
   - *Assessment:* **Moderate.** Prior works like Memory-R1 use opaque RL policies; FadeMem uses LLM heuristics (semi-transparent); PAMU is rule-based but only for preferences. ASK’s combination of interpretable features (c,e,f,r,ρ) and linear scoring is distinct. We should say it is novel to use a *hand-designed scorecard* in this domain.
   - *Support:* Most controllers are RL or hidden (MemR1) or are heuristics for specific tasks (PAMU uses domain-specific stats).
   - *Threats:* Some MLP or linear controllers may exist in literature, but none cited here.
   - *Verdict:* **Moderate** novelty – emphasize design rather than claim never done.
   - *Safer wording:* “ASK uses a hand-crafted, transparent scorecard policy for revision, unlike prior learned or heuristic-only schemes.”

5. **“ASK introduces action-level evaluation for memory governance.”**
   - *Assessment:* **Moderate-Strong.** Action-level or per-operation correctness metrics are rare. HaluMem does per-step hallucination tests, but not in a memory agent context. ASK’s “revision correctness” metric seems novel. We should likely consider this moderately novel – maybe say “rarely done in prior work”.
   - *Support:* HaluMem is the only somewhat similar, but it is a benchmark, not memory system evaluation.
   - *Threats:* If any unpublished work or industry uses, but not found.
   - *Verdict:* **Moderate**. Claim careful novelty (action-level evaluation is uncommon in literature).

6. **“ASK’s novelty is the conjunction of [lineage + abstention + transparent policy + action evaluation].”**
   - *Assessment:* **Moderate.** This combined claim is strongest: individually, each component appears in some form, but together they form a unique package. We should state that while each element has precedent, *no prior work integrates all of these*.
   - *Support:* As above, each piece has parallels, but no single system does them all.
   - *Threats:* We must not overstate uniqueness; but likely no system does all.
   - *Verdict:* **Moderate**. This is a defensible “novel contribution” as a system.

**Summary:** The literature contains hints of ASK’s ideas, but no existing system fully covers them. Particularly, explicit abstention and user-level version lineage appear new. We will frame novelty as the **combination of known techniques** applied in a new way, rather than claiming any one subcomponent is unprecedented.

Below are three draft thesis positioning statements, from conservative to strong:

**Conservative (For defense):**
> *This thesis proposes ASK, a memory governance framework for personal LLM assistants. We build on recent work in LLM memory (e.g. dynamic update agents and temporal memory graphs) but extend it with explicit operations to keep, supersede, or abstain from updates. To our knowledge, no prior agentic memory system has jointly combined (a) typed user memory entries, (b) versioned supersession links, (c) an explicit “abstain” option for uncertain updates, and (d) a transparent, feature-based decision policy. We design a linear scoring controller over evidence and confidence features, and evaluate it both end-to-end and at the operation level using new diagnostics. Our contribution lies in integrating these elements to improve long-lived personalization, rather than in any single component alone.*

**Strong but Defensible (For abstract/introduction):**
> *We introduce a novel memory-governance approach for LLM assistants that decides whether to keep, overwrite (supersede), or refuse new user-provided memories. Unlike prior systems that simply append or heuristically prune memories, our method uses a transparent feature-based policy to compare incoming information against existing memory items. Key new aspects include typed memory categories (stable vs. transient preferences, episodic facts), explicit supersession links (version lineage) when facts change, and an abstention action when evidence is insufficient. We demonstrate that incorporating these features yields more reliable memory behavior: action-level metrics show higher revision accuracy and lower hallucinations than baselines. In the reviewed literature, we did not find an existing system that combines all of (lineage tracking + abstention + a scorecard policy + per-action evaluation) for personalized LLM memory.*

**Publication-Oriented (For future paper):**
> *We propose a **revision-control layer** for LLM assistant memories that transparently manages updates. Our system maintains typed memory entries (preferences vs. facts) with timestamps and evidence. For each new user claim, it computes two interpretable scores-one for “supersede” (confidence-weighted recency) and one for “abstain” (uncertainty/hedge)-and chooses among {Keep, Supersede, Abstain} via simple thresholds. We log explicit lineage when memories are superseded. This feature-based controller outperforms naive baselines (no memory, flat RAG, recency prune) on both question-answering accuracy and per-update precision. Crucially, we propose **action-level** metrics (revision correctness, over/under-forgetting rates, abstention precision/coverage) to complement standard QA evaluations. To our knowledge, no existing agentic memory system offers both explicit abstention and versioning in a self-contained, interpretable framework. Our contributions are thus the combination of typed versioned memory, abstention-as-action, and an evaluated revision policy.*

# 9. Literature Review

**Memory as Context and Retrieval.** Early work on LLM memory treated it as external context expansion. Retrieval-Augmented Generation (RAG) approaches back LLMs with documents or vectors. For example, *MemoryBank* (Zhong et al., 2024) stores user-specific “memories” in a vector DB and uses periodic summaries and decay schedules to forget old info. Likewise, *Generative Agents* (Park et al., 2023) continuously log all user observations and reflections, retrieving relevant memories by similarity or recency. These systems successfully endow chatbots with longer “attention spans,” but they do not consider *revision*: if a user contradicts an earlier memory or refines a preference, these frameworks typically just append the new data. There is no built-in logic to retract or skip memory entries. The result is often data accumulation and confusion: systems may overweight stale facts or hallucinate conflicts.

*Limitations:* RAG-like systems overlook the dynamics of personal memory. As pointed out by Wu et al. (2025), real users do *update* their story (e.g. "I now live in Boston" vs earlier "I live in NYC"), requiring the agent to *know when to overwrite*. In fact, the LongMemEval design explicitly includes “knowledge updates” as a test. But static retrievers have no mechanism for this beyond indiscriminately retrieving the latest-supplied facts (which may be wrong). They also suffer from “lost in the middle” biases and cannot handle indefinite horizons without external memory.

**Explicit Memory Operations.** More recent agents have introduced explicit lifecycle control. *Memory-R1* (Yan et al., 2025) trains an RL policy to choose per-memory actions (ADD, UPDATE, DELETE, NOOP) given a QA task. This model learns when to update a slot versus discard it. Similarly, *Reflective Memory Management (RMM)* (Luo et al., 2025) performs a two-stage routine: after each session, it summarizes content and then either **merges** it into an existing memory entry (if relevant) or **adds** a new entry. Merging is akin to UPDATE, and adding is ADD; RMM has no DELETE or explicit NOOP. Another example, *A-MEM* (Xu et al., 2025), structures each memory (Zettelkasten notes) and **links** similar memories, effectively updating them. These systems show that treating memory changes as actions can improve performance.

Yet, a gap remains: none of these methods allow the agent to *refuse* updating when the new information is dubious. RMM always merges or adds, and Memory-R1 always executes an operation. In contrast, ASK explicitly models an **abstain** choice. The **Selective Prediction** literature suggests this is valuable: allowing a model to say “I don’t know” can boost reliability. ASK formalizes this for memory writes.

**Contradiction and Drift.** Another stream addresses inconsistent or changing information. *FadeMem* (Wei et al., 2026) uses an LLM to classify how a new memory relates to existing ones (compatible, contradictory, subsumes, subsumed). If contradictory, the old memory is suppressed (faded); if subsumed, contents are merged. This dynamic forgetting mimics how humans revise beliefs. PAMU (Sun et al., 2025) targets preference drift: it compares short-term vs long-term preference distributions, updating the long-term model only when a significant change occurs. Both systems aim to prevent outdated info from polluting memory.

ASK similarly wants to handle these cases, but through a different mechanism. Instead of LLM classification (like FadeMem) or statistical tests (like PAMU), ASK uses interpretable features (confidence, negation markers, recency, etc.) to score the trust in new info. If contradictory or hedged (`f` high, low `c`), the controller will lean toward **Keep** or **Abstain**, avoiding risky updates. ASK logs supersession explicitly (unlike FadeMem’s implicit suppression) and makes **abstention** a formal outcome (unlike FadeMem/PAMU, which always integrate new info eventually). Thus, ASK’s approach is rule-based and transparent: a human could inspect why a given new memory was kept or ignored by examining the feature values, whereas RL or black-box methods cannot.

**Provenance and Temporal Memory.** Trustworthy memory requires knowing *what changed when*. ASK stores evidence spans and “supersedes” links, akin to a temporal database. This idea has precedents: the Zep/Graphiti system (Rasmussen et al., 2025) represents memories as a temporal graph. Facts have validity intervals and can be queried “as of” any time. Similarly, MemOS (Li et al., 2025) uses MemCubes that include version history metadata. These ensure *non-lossy* memory: old facts aren’t deleted. ASK’s novelty is to embed this provenance in a personalized agent, tying it to user sessions. By contrast, Zep is more like a knowledge graph service; ASK is an interactive agent memory.

No prior agentic memory work combines provenance with a policy for updates. (One could store a timestamp without using it, but ASK uses time recency in scoring too). ASK’s action log (recording every decision and feature values) aligns with calls for *auditability* in memory. This makes our system more explainable and debuggable, reducing risks like “semantic drift” identified by SSGM.

**Benchmarks and Evaluation.** The community has begun to quantify memory behavior with new datasets. Benchmarks like **LongMemEval** (2025) and **ES-MemEval** (2026) explicitly test knowledge updates and abstention. For example, LongMemEvalₛ includes “knowledge supersession” questions (e.g. “Has Alice changed jobs since last mention?”) and requires models to say “don’t know” when appropriate. ASK is evaluated on these downstream tasks, confirming that its memory scheme actually improves end-user answer quality.

However, these end-to-end metrics alone do not reveal *why* a system succeeds or fails. As HaluMem (Chen et al., 2025) shows, errors often originate in the memory storage stage, yet benchmarks usually credit or blame the final answer. Thus ASK introduces action-level metrics. We label each update as **correct** or **incorrect** (relative to a ground truth which we craft for evaluation), and compute precision/recall of Supersede vs Keep vs Abstain decisions. We also define “over-forgetting” (dropping facts too eagerly) and “under-forgetting” (retaining stale data). This fine-grained evaluation illuminates behavior that pure QA scores miss. For instance, two agents might answer a question equally well by chance, but one could be mismanaging memory. ASK’s diagnostics ensure we catch such cases.

**Limitations of Prior Work:** In summary, no existing system fully addresses ASK’s narrow problem of *interpretable revision control*. A common theme in past work is either *excessive inertia* (always keep) or *excessive plasticity* (always overwrite). RMM merges everything, FadeMem fades everything contradictory, Memory-R1 updates whenever trained. We did not find any system that explicitly *refuses* to update when evidence is weak. The concept of an agent saying “I’m not sure” to memory is novel. Similarly, the idea of scoring each incoming fact on features like negation or hedging is unique.

Therefore, ASK’s contribution lies in combining best practices from many areas: RAG for retrieval, dynamic update operations, conflict detection, and selective abstention. It should be characterized not as an isolated breakthrough in one piece, but as a coherent integration. The most defensible claim is that **the joint design of typed memory with explicit lineage, a selective (supersede/abstain) update policy, and an action-level eval is new**. We must ensure the thesis frames novelty as integrative, not singular.

**Why QA accuracy is insufficient:** Finally, we emphasize that downstream QA accuracy (even on benchmarks) can be misleading. A model might answer correctly by luck, or by clever prompt engineering, without actually having stable memory. For memory governance research, we need to verify *each* memory action. That’s why ASK’s evaluation suite (LongMemEval-S + MGP-6) is designed to separate memory from inference. For example, after a memory is incorrectly discarded, future QA may still be right if the model retrieves info elsewhere, hiding the mistake. Only by testing the memory updates directly (revision correctness) do we ensure the agent truly learned the intended policy.

In sum, ASK builds on the literature but occupies a distinct niche: governance of personal memory via explicit, interpretable rules and metrics.

# 10. Research Gap

While recent work has advanced LLM memory along multiple fronts, **no prior system explicitly integrates a selective, explainable revision policy with typed, versioned memory entries**. Retrieval-augmentation and static memory logs provide baseline storage but cannot handle evolving user information. Lifecycle managers (Mem0, MemOS, RMM, Memory-R1) have introduced update operations and even versioning, yet they lack a mechanism to *decline uncertain updates*. Conflict-aware models like FadeMem apply aggressive forgetting or merging, but do not include an abstention choice nor fine-grained lineage tracking. Benchmarks (LongMemEval, ES-MemEval) include abstention and revision questions, highlighting the need, but they measure end results only. In the surveyed 2024–2026 literature, we found **no agentic memory system that (a) categorizes memories by type, (b) maintains explicit supersession links, (c) uses a transparent score-based rule for Keep/Supersede/Abstain, and (d) evaluates each memory action’s correctness**. This gap motivates ASK: our thesis proposes precisely this integrated approach to ensure personalized LLM memory remains consistent, up-to-date, and auditable.

# 11. Contribution Paragraph

The contributions of this thesis are as follows. First, we define a **typed memory representation** for LLM assistants (stable vs. transient preferences, episodic facts) with rich metadata (timestamps, confidences, evidence text, and explicit *supersession* links). Second, we introduce a **revision controller** that decides-on a per-item basis-whether to **Keep** the prior memory, **Supersede** it (overwrite with the new fact, logging the supersession), or **Abstain** (defer update when evidence is insufficient). Unlike black-box policies, our controller is a transparent feature-based scorecard, using interpretable signals (extraction confidence, span recency and specificity, negation/uncertainty markers, and type stability). Third, we propose new **action-level evaluation metrics** (revision correctness precision/recall, over-/under-forgetting rates, abstention coverage) to diagnose memory behaviors that end-to-end QA accuracy cannot capture. Finally, we empirically show that the **combination** of typed versioned memory + explicit lineage + abstention + transparent updates outperforms naive baselines (no memory, flat RAG, recency-prune, overwrite) on synthetic and real chat tests. In summary, ASK’s novelty lies not in any one idea, but in unifying known components into a coherent memory governance framework for personalized LLMs.

# 12. Threats to Validity

Several limitations of our approach and evaluation should be noted:

- **Synthetic Datasets and Benchmarks:** The primary evaluation datasets (LongMemEval-S and MGP-6) are synthetic or semi-synthetic. *LongMemEval-S* borrows scenarios from curated logs, but still may not capture real-world dialogue complexity. *MGP-6*, our action-level test set, was author-generated. As such, it might not reflect all types of memory errors or user intentions. The results may overfit these specific scenarios. In future work, we would validate on a public or larger benchmark (though none currently exist for this exact problem).

- **LLM Judge Reliability:** We rely on an LLM (GPT-4o) to judge QA answers. While prior work reports >97% agreement with human judges on LongMemEval, automated judging is still imperfect. Mistakes by the judge could mis-evaluate downstream QA performance. We mitigate this with bootstrapped confidence intervals, but note that GPT-judge errors may bias the results.

- **Memory Extraction Errors:** Our pipeline uses an extractor to identify candidate memories from user chat. Extraction is not perfect, so some user-supplied information may be missed or garbled. If the input to the controller is faulty (e.g. “no memory” evidence provided), the controller can’t fix that. Thus, part of ASK’s errors may come from upstream NLP (relation classification, coreference, etc.) rather than the controller itself.

- **Relation-Classifier Noise:** ASK uses an LLM to classify the signed relation `r` (positive or negative stance of the new statement). This classifier can err (e.g. due to subtle sarcasm or ambiguous wording), causing `r` to have wrong sign. Since `r` influences both supersession score and abstention score, such errors can flip decisions. We did not deeply ablate the classifier accuracy, but it’s a clear risk to reliability.

- **Limited Action Set:** We restrict actions to three. In reality, a memory manager might benefit from more granular options (e.g. *fine-grained merge*, *split*, or *later review*). The chosen actions may oversimplify some cases. Additionally, the thresholds (θ_sup and θ_abs by type) were manually tuned; different values might change trade-offs significantly. We should consider that our design space is not exhaustive.

- **Sample Size and Domain:** The number of test queries (and memory operations) we evaluate is relatively small compared to commercial systems. We mostly tested on variants of available benchmarks and our diagnostic set. User diversity (different writing styles, domains) is limited. The controller weights were calibrated on a development set, risking overfitting. Real users may express uncertainty or contradictory information differently.

- **Judge Model Dependence:** For some tasks (like factual consistency in memory), we rely on an LLM as a “judge”. This implicitly assumes the LLM is well-calibrated. If the judge model shares biases with the memory LLM, evaluations could be skewed (the judge might be more lenient or harsher on certain phrasing).

- **Overclaiming Novelty:** We have been careful not to assert absolute novelty for each component. However, there is always a risk of unintended “scoping out” of related work. For example, industry systems or unpublished prototypes might implement similar ideas. We consider the likelihood low given our searches up to mid-2026, but acknowledge that memory agent research is rapidly evolving.

- **Temporal Relevance:** New systems (e.g., Light memory in BEAM or future drift detectors) may emerge. Our comparisons are based on literature up to June 2026. We note this to avoid claiming the final word on the field.

- **Limited Real-User Validation:** We have not tested ASK with actual users over time. User studies (like CareCall’s study showed engagement with memory), are needed to confirm that ASK’s behavior aligns with user expectations. It’s possible that too much abstention feels unhelpful, or that transparency details are not valued by end-users.

Despite these threats, we believe our findings about action-level revision control are robust within the tested scope, especially given we compare against strong baselines and use bootstrapping for statistical estimates. We also cross-checked decisions manually for a subset. But future work should expand datasets, include user feedback, and verify that the controller’s weights generalize.

# 13. Future Work

**Master’s-scale extensions:** There are several straightforward ways to strengthen this study within a Master’s project timeline.
- **RL-Control Baseline:** Implement a learned controller (similar to Memory-R1) over the same features or a neural policy. Compare its performance and interpretability to our rule-based controller. This could clarify how much gain (if any) comes from learning versus hand-crafting the policy.
- **Better Judge Models:** Use or fine-tune larger or specialized LLM judges (e.g. models fine-tuned on factuality) to improve the reliability of automatic QA and hallucination assessments. A targeted calibration might reduce judge noise in LongMemEval evaluations.
- **Advisor/Expert Feedback:** Conduct limited user studies or expert evaluations of system behavior. For instance, recruit volunteer “users” to correct the agent’s memory in an interactive setting, providing a more natural evaluation of revision quality than synthetic tests.
- **Feature Ablations:** We used five features (c,e,f,r,ρ). An ablation study (e.g. drop one feature at a time) could measure each feature’s importance empirically. Particularly, test whether simpler rules (e.g. only confidence-based) yield similar results.
- **Memory Typology Variants:** Explore more memory types (e.g. location of truth vs opinion) or refine existing ones. Perhaps add a “dispreferred_facts” type or tag. Evaluate if the controller needs type-specific thresholds or weights.

**PhD-scale extensions:**
- **Large-Scale Benchmark and Annotation:** Expand MGP-6 into a larger, publicly released benchmark for memory revision (with multiple annotators). This would involve crafting many more scenarios of updates, contradictions, and ambiguous statements, possibly across different domains. The benchmark could be a resource for the community.
- **Rigorous Belief Revision Framework:** Link ASK’s policy to formal theories of belief revision (AGM postulates). This could ground the action rules in logic or probability theory. For example, interpret `r` as a sign of belief, and analyze whether ASK’s decisions satisfy consistency or minimal change principles.
- **User Studies:** Deploy ASK in a small-scale personal assistant prototype. Observe real users over days or weeks to see if the system’s memory updates match users’ expectations and if it avoids frustrating errors. This can reveal unanticipated issues in natural dialogue.
- **Temporal Graph Integration:** Integrate ASK’s memory with a temporal knowledge graph (like Graphiti). Then updates would also populate a global timeline. This could facilitate queries like “what was Alice’s address last year?” and connect personal memory to factual events.
- **Calibration and Uncertainty:** Incorporate probabilistic confidence (e.g., Bayesian calibration) to improve the abstention mechanism. One could measure Expected Calibration Error (ECE) of `c` or `S_abs`. Also consider multi-pass deliberation: if `S_abs` is near threshold, request clarification from user rather than a hard Abstain.
- **Taxonomy of Memory Failures:** Systematically characterize failure modes of memory governance (overwriting too much, hallucinating, privacy leaks, etc.) and design metrics for each. For instance, test “overcommitment” scenarios where the agent erroneously infers something from scant hints.
- **Interoperability with Systems:** Evaluate ASK as part of a multi-agent or multi-tool system (like an AI with long-term memory API). Study how it could be combined with retrieval or knowledge bases.
- **Open-Source Release and Community Benchmarks:** Release ASK code and memory datasets for others to test. Engage with benchmarks like LoCoMo/LongMemEval/BEAM to establish baseline numbers for memory governance. Perhaps organize a shared task on memory updates for LLMs.

By pursuing these extensions, one could move from a thesis prototype to a robust, validated system. The overarching future goal is to build LLM assistants whose long-term memory is as reliable and human-aligned as possible.
